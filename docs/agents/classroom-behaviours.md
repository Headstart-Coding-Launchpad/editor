# Agent Reference: Classroom Behaviours

Load this when a task touches student/teacher classroom behaviour, live view, broadcast, sandbox, Pyodide, or carry-through.

## Code Carry-Through

- Check localStorage for the authored carry source before loading starter content.
- If the immediate carry source has no saved state, walk the authored carry chain to the first earlier source with saved state. If the chain ends without saved state, use the current task starter content.
- Authored carry references can cross group boundaries; groups do not limit carry resolution.
- Saved empty content counts as real saved state; do not walk past it.
- HTML lessons carry each current `starterFiles` file independently by filename. Files not named in the current task remain hidden.
- Python and HTML use `carryCodeFrom`; Scratch uses `carryBlocksFrom`; filesystem uses `carryFsFrom`; electronics uses `carryCircuitFrom`.
- Live students write `carryFallbackLog/{anonymousId}/{taskId}` when carry-through walks past the immediate source and finds an earlier saved state. Session reports surface this as per-student `carryFallback` metadata plus task-level `carryFallbackCount`/`carryFallbacks`.
- Teacher presentation and builder preview persist to an in-memory ephemeral store (`ephemeralStorage` in `studentStorage.js`, routed via `createStudentPersistence`) so carry-through works there without reading or polluting real localStorage. The store is cleared on each presentation/preview mount. All persistence in these modes keys off `effectiveIdentity` (`teacher-presenter` in presentation).

## Live View: `activeStudentView`

- Default expanded student view shows the last-run snapshot only; it does not stream.
- Streaming starts only when the teacher clicks "Go Live".
- On "Go Live", fetch once first, then set `activeStudentView`.
- While live, teacher sees the student's selected text/cursor plus short copy, paste, and click notices.
- Closing the modal by any route must clear `activeStudentView`: close button, outside click, Escape, or tab close.
- Firebase `onDisconnect` clears `activeStudentView` on unexpected teacher tab close.
- Only one student streams at a time.
- Scratch has the same live-view standard as Python/HTML, extended with sprite/stage motion and a live cursor:
  - Block drags, block clicks (click-to-run), green-flag, stop, and sprite drags on the stage surface as short notices via `LiveActivityToast` (`currentActivity`/`teacherLive.activity`, same generic `{ type, at }` shape as copy/paste/click).
  - `ScratchWorkspace`'s stage canvas mirrors live sprite motion, not just authored starting positions: `onSpriteStatesChange` (`ScratchWorkspace.jsx`) publishes a throttled (~120ms) `{ spriteStates, cloneStates, backdropName }` snapshot to `currentSpriteState`/`teacherLive.spriteState`, and a read-only mirror instance loads it via the `externalSpriteState` prop without ever running the interpreter.
  - Block *content* mirroring is different from the sprite/cursor/block-drag mirrors above: those render purely from a mirror-only React state, but the `externalState`/`externalStates` "teacher push" effect calls `loadWorkspace` (`scratchPersistence.js`), which mutates the real, shared Blockly workspace object in place — there is no separate mirror instance to discard when the broadcast ends. `StudentWorkspace.jsx` (scratch module) therefore tracks the `isForcedTeacherLive` true→false edge and bumps a `liveEndEpoch` counter into `ScratchWorkspace`'s `key`, forcing a real remount so the workspace rebuilds from the student's own saved state — without this, the workspace keeps physically holding the teacher's last-broadcast blocks after "Go Live" ends, and the student's next edit persists them as their own saved code.
  - A live pointer dot tracks the source's mouse over both the stage and each sprite's Blockly block workspace (throttled ~50ms, `currentCursor`/`teacherLive.cursor`, shape `{ target: 'stage' | 'workspace', spriteId, x, y, at }`). The mirror's visible sprite tab automatically follows the source's tab whenever a workspace-target cursor is live. A cursor with no update for 2s fades out rather than freezing in place.
  - A block actively being dragged streams its own live position too (`currentBlockDrag`/`teacherLive.blockDrag`, `{ spriteId, blockId, x, y, at }`), read straight off Blockly's own drag-tracked coordinates and cleared to `null` when the drag ends — without this, the mirror only ever saw the settled block state on drop (debounced ~1s), so a dragged block would jump into place rather than visibly follow. The mirror moves the block via Blockly's `moveTo` (a plain reposition, not a real drag) and only if that block already exists in its last-synced state.

## Scratch Compact Layout: Instructions/Code and Blocks/Stage tabs

- The response to a shrinking panel is graduated, and — deliberately — the explainer gives way *before* the code area (Blocks/Stage) is ever forced to compact, not after. `LessonTaskContent.jsx` measures its explainer+workspace container (`useElementSize.js`, a `ResizeObserver` hook) and, for Scratch lessons only:
  1. **Split**: the explainer renders at a **fixed, non-resizable width** (`EXPLAINER_FIXED_WIDTH`, 400px — Scratch explainers often carry block-pill images/markdown that need real width) alongside the code area — no `SplitPane`, no drag handle, no percentage math. Deliberately simpler than a shrinking/pinning split: it's either 400px or a tab, nothing in between. This is a plain fixed-width flex layout, not a `SplitPane` change — every other lesson type (Python/HTML/Arcade/Electronics) still uses `SplitPane`'s draggable percentage split, untouched.
  2. **Instructions tabs away**: `LessonTaskContent` switches Instructions/Code to `PanelTabs` as soon as a fixed 400px explainer (plus the `s.scratchFixedSplit` gap between the two columns) would leave the code area under `ScratchWorkspace.jsx`'s own "wide" width — `EXPLAINER_FIXED_WIDTH + SCRATCH_SPLIT_GAP + SCRATCH_CODE_WIDE_WIDTH` (400 + 12 + 1000 = 1412px combined), where `SCRATCH_CODE_WIDE_WIDTH` is `ScratchWorkspace.jsx`'s exported `NARROW_BREAKPOINT`, imported rather than duplicated so the two thresholds can't drift apart. This is *before* the code area would otherwise be squeezed — the Code tab then gets the *entire* panel width, so Blocks/Stage stay side-by-side rather than being forced into their own compact tabs. Width-only: height doesn't factor in, since giving Code its own tab doesn't add height (explainer and code already share the same row).
  3. **Stage tabs away from Blocks — the final fallback**: only if the panel is so narrow that even giving Code the *entire* width still leaves it under `ScratchWorkspace.jsx`'s own `NARROW_BREAKPOINT` (1000px) does `ScratchWorkspace.jsx` — which independently measures its own real rendered container — switch to its own Blocks/Stage `PanelTabs` switcher, replacing the old `preferStageSidePanel`/auto-collapsing-stage-rail behaviour. No coordination code is needed for this step beyond the shared constant above — it otherwise falls out of each component measuring its own real rendered size. Width-only, same as step 2: a short-but-wide container doesn't trip this at all — it scales the stage down instead (see the `computeStageScale` note below). Unconditional for the teacher-modal `TeacherLiveView` (`forceCompact`, see below), regardless of width or height.
  The pre-existing manual explainer collapse-to-rail toggle (`explainerCollapsed`, `CollapseTabButton`/`CollapsedPanelRail`) still works within step 1, unrelated to any of the above — it's a separate, purely user-initiated affordance, not part of the automatic ladder.
- Tabs never unmount the inactive pane — this preserves live Blockly workspaces, a running Scratch program, and live-view mirroring (see below) regardless of which tab a student or viewer currently has open. `ScratchWorkspace.jsx`'s own Blocks/Stage tabs use the shared `PanelTabPanel` (`display:none` on the inactive one). `LessonTaskContent.jsx`'s outer Instructions/Code split does the same thing but *inline* rather than via `PanelTabPanel` — the explainer and code panes are the same two `<div>`s, in the same tree position, in *both* split and compact mode; only their `style` differs. This isn't just a style choice: if compact and split rendered structurally different trees at this position (as they briefly did — see the gotcha below), React would unmount and remount everything below on every threshold crossing, including every Blockly workspace inside `ScratchWorkspace`.
- The last-active tab is remembered per device via `localStorage` (`layoutTabStorageKey`/`loadLayoutTab`/`saveLayoutTab` in `studentStorage.js`, keys `headstart_layout_task_panel` and `headstart_layout_scratch_panel`) — unscoped, since it's a display preference rather than lesson/task state. With nothing yet persisted, the Instructions/Code switcher defaults to **Code** (the Blocks/Stage switcher defaults to **Blocks**) — a student landing in compact mode sees their workspace first, not the explainer.
- The wide-layout manual stage-panel rail-collapse (`stagePanelCollapsed`, the `CollapseTabButton`/`CollapsedPanelRail` pair) still exists above the compact threshold, but is now purely user-toggled — nothing auto-collapses or auto-restores it.
- The teacher dashboard's "watch one student" modal (`StudentModal` → `StudentWorkspaceBody.jsx`) renders `scratch/TeacherLiveView.jsx`, which always forces the compact Blocks/Stage layout (`forceCompact`) regardless of the modal's own width — this replaced a direct, non-compact `ScratchWorkspace` render that could show a different collapsed panel than the student's own screen at the same width.
- `code_arrange` tasks are the analogous case for `StudentModal`: `deriveTaskContext()` (`src/shared/taskUtils.js`) only derives `isPython`/`isHtml` from the lesson module type, so a `code_arrange` task still trips those flags. `StudentWorkspaceBody.jsx` checks `isCodeArrangeTask` (`task?.taskType === 'code_arrange'`) before the `isPython`/`isHtml` branches and renders the real `CodeArrangeTask` tile board — read-only, with `selectedAnswer` reconstructed from `student.currentCode`/`currentFiles` via `deriveSlotStateFromCode()` (`src/shared/codeArrange.js`) — instead of falling through to a raw read-only `CodeEditor` showing the fully assembled program text, which didn't match what the student was dragging tiles into.
- The student grid (`StudentCard.jsx`) shows a "👀 Info + Blocks + Stage"-style badge summarising what a student can currently see, live-synced to `sessions/{lessonId}/students/{anonymousId}/visiblePanes` via `writeStudentPresence`. Every lesson type feeds this now, via two different paths in `LessonTaskContent.jsx`:
  - **Scratch** (the original case, where the explainer/code split itself hides a pane): `ScratchWorkspace.jsx` derives its own `['blocks']`/`['stage']`/`['blocks','stage']` from `hideStage`/`compact`/`activePane`/`stagePanelCollapsed` and reports it via `onVisiblePanesChange`; `LessonTaskContent.jsx` combines that with its own Instructions/Code tab state (`taskPanelCompact`/`taskPanelTab`) into the final array, held in its `scratchCodePanes` state.
  - **Electronics, Python, Arcade, HTML** (module-internal toggles, gated by `MODULE_PANES_TYPES`): each module's own `StudentWorkspace.jsx` reports its togglable state directly into `LessonTaskContent.jsx`'s generic `modulePanes` state via the same `onVisiblePanesChange` prop — Electronics reports `[selectedTab]` (`'breadboard'`/`'code'`, via `ElectronicsWorkspace.jsx`'s `onTabChange` effect, which also fires for the teacher-controlled `activeTab` prop); Python reports `['code']` or `['code','console']` from `outputCollapsed` (only when the output pane is actually rendered — never for submit-mode tasks); Arcade reports `[workspaceTab, ...(running ? ['running'] : [])]`; HTML reports `[activeFile, ...(previewVisible ? ['preview'] : [])]` (the file name passes straight through `StudentCard.jsx`'s `VISIBLE_PANE_LABELS` map unmapped, since file names are dynamic).
  - **The `instructions` entry itself** is computed once, centrally, in `LessonTaskContent.jsx` (`instructionsPaneVisible`) and merged into whichever of the two paths above applies — it does *not* come from a module's own `onVisiblePanesChange` report. It's `false` whenever the task has no explainer at all (quiz/information/sandbox); otherwise it follows whichever collapse mechanism is actually rendered: the compact tab (`taskPanelTab === 'instructions'`), the side-rail collapse (`!explainerCollapsed`, Scratch and every other `SIDE_EXPLAINER_TYPES` lesson type on desktop), or `ExplainerPanel`'s own accordion collapse (`!accordionExplainerCollapsed`, reported upward via its `onCollapsedChange` prop — used by Filesystem, which has no side-rail layout, and by every type's mobile fallback).
  - **Filesystem** has no `MODULE_PANES_TYPES`/side-explainer entry and reports no internal panes of its own — but it still reports `['instructions']`/`[]` (via the `instructionsPaneVisible` merge above, gated on `hasTaskExplainer` alone rather than `isScratchLesson`/`supportsModulePanes`), so its Info badge still works even though it has nothing else to report yet.
  In both paths, `LessonTaskContent.jsx` hands the final array to `StudentView.jsx`'s `onVisiblePanesChange`, which writes to Firebase only for a real student in a live/sandbox session (never `teacherPresentation`), deduped against the last-written value.
- **Gotcha #1 — stale measurement across task navigation**: `TaskSlideTransition.jsx` keys its child wrapper by `transitionKey` (one per task), so on every task navigation React tears down and rebuilds the panel's DOM node *without* `LessonTaskContent` itself remounting — its hooks (and any state they hold) persist across that swap. `useElementSize.js` therefore uses a callback ref, not `useRef` + a mount-only effect: a plain effect would only ever have attached to the very first task's DOM node, then silently kept "observing" that now-detached node forever, freezing the measured size (and therefore the compact-tab decision) at whatever it happened to be on the first task loaded — intermittent-looking bug reports ("sometimes it's compact, sometimes it isn't, I can't tell why") after navigating between tasks trace back to this. `ScratchWorkspace.jsx` doesn't have this problem — its `StudentWorkspace.jsx` caller gives it a task-scoped `key` too, so it *does* fully remount (deliberately, to re-inject Blockly) and its own resize effect sets up fresh each time.
- **Gotcha #2 — remounting ScratchWorkspace on every compact/split crossing**: earlier revisions rendered the outer Instructions/Code split and the outer Instructions/Code tabs as structurally different trees (one used `PanelTabPanel`, the other plain `<div>`s) at the same position in `LessonTaskContent.jsx`. Since these differ in element/component type, React can't reconcile between them — every time `taskPanelCompact` flipped (i.e. every time the panel crossed the 1412px boundary while resizing), it unmounted the *entire* subtree below, including `ScratchWorkspace` and every Blockly workspace it had injected, then mounted a fresh instance. A freshly-mounted `ScratchWorkspace` starts non-compact until its own `ResizeObserver` reports back — normally self-corrects within a frame, but repeated remounts (e.g. resizing back and forth across the boundary a few times) could leave it stuck showing Blocks/Stage as tabs even at a width where it should be side-by-side, matching reports like "the stage stays collapsed until everything is wide open." Fixed by keeping the explainer/code panes as the same two `<div>`s regardless of mode (see above) — see `src/app/components/__tests__/LessonTaskContent.test.jsx`'s mount-count regression test.
- **Blockly zoom is fully automatic — there is no manual wheel-zoom or on-canvas zoom control.** `ScratchWorkspace.jsx` continuously recomputes a block scale (`computeBlockScale(width, height)`, a pure exported function) from the same container measurement used for `compact`, between `BLOCK_SCALE_MAX` (0.75, the old fixed default) at/above the wide reference size and a `BLOCK_SCALE_MIN` readability floor (0.6) as the container shrinks within compact territory — applied via `ws.setScale()` on every sprite's workspace inside `resizeBlocklyWorkspaces`. Manual zoom was removed deliberately (not just left disabled) so this auto-adjustment never has a student's own zoom choice to fight, mirroring why the stage-panel auto-collapse was replaced with tabs rather than kept as an auto-toggle. The mouse wheel now pans instead of zooming.
- **A shrinking panel scales the stage instead of hiding it or forcing a scroll.** `scratchTaskPanelWrap` carries no height floor (`minHeight: 0`, same as every other fluid-workspace lesson type) — a taller sibling (the completion banner wrapping onto more lines, a status banner appearing above the workspace, etc.) is free to shrink it as far as it needs to. `ScratchWorkspace.jsx`'s `computeStageScale(width, height, { compact, flyoutCollapsed })` (pure, exported, unit-tested) takes the *smaller* of a width-derived and a height-derived scale factor — the height factor reserves `STAGE_TOOLBAR_HEIGHT_RESERVE` (52px) for the stage toolbar above the canvas — so the stage's rendered size shrinks continuously down to a `MIN_STAGE_SCALE` (0.35) floor as height drops, the same way it already shrunk with width. This replaced an earlier approach (a hard `minHeight` floor on `scratchTaskPanelWrap`, propagated through two ancestors via `minHeight: 'auto'` overrides, `TaskSlideTransition`'s now-removed `panelStyle` prop among them) that kept `ScratchWorkspace` from ever measuring short — which avoided tripping the old height-based compact threshold, but did so by making the page scroll to keep the panel at its floor height, which could scroll the stage out of view entirely. Compact itself is now width-only (see step 3 above); height is handled entirely by scaling.
- **Stage emoji fallback rendering can flip fonts on first paint.** A sprite/clone without a costume image falls back to drawing its `emoji` field on the canvas (`drawEmojiAtOrigin`), styled `'Noto Color Emoji', serif` — a Google Fonts web font loaded page-wide via `index.css`'s `@import` (`font-display: swap`). Canvas text doesn't repaint itself once a swapped-in web font finishes loading the way DOM text does — whatever font was available at the moment `fillText()` ran is what stays drawn, even after the real font loads, until something else happens to trigger a redraw. `ScratchWorkspace.jsx` explicitly awaits `document.fonts.load(...)` once per mount and bumps `imageVersion` (the same "force a stage redraw" counter the backdrop/costume image-preload effects use) once it settles, so both the stage canvas and the `SpriteThumb` sprite-panel thumbnails (which already redraw on `imageVersion`) always end up showing the correct emoji font rather than whichever one happened to be ready first.

## Teacher Code Highlights: `teacherHighlights`

- Independent of `activeStudentView`/`teacherLive` — a teacher watching a student live (`StudentModal`) can select a character range in the mirrored, read-only `CodeEditor` and tag it with an emoji + optional short note.
- Stored as a map at `sessions/{lessonId}/students/{anonymousId}/teacherHighlights/{highlightId}` (RTDB `push()` keys, so any number can coexist across files/lines) — written by `pushTeacherHighlight`/`removeTeacherHighlight` in `useSession.js`.
- Each entry: `{ file (encodeFileKey'd), from, to, emoji, note, createdAt }`. Python tasks use an empty string for `file` (single-file, no tabs).
- Renders as a `Decoration.mark` + clickable emoji badge (`teacherHighlightsField` in `src/shared/CodeEditor.jsx`) in **both** the teacher's mirror and the student's own editable editor — the same dual-instance path `remoteSelection` already uses.
- Clicking the emoji badge removes that highlight (`onHighlightDismiss`) — this lets the teacher retract their own highlight from the mirror, or the student dismiss it from their own editor. Either side writes the same RTDB removal.
- Ranges are character offsets valid for the document as of creation; CodeMirror remaps them through edits within the same browser session, but a highlight can drift if the student reloads after edits happened elsewhere in the file — accepted tradeoff for character-exact (vs line-snapped) precision.
- Cleared automatically on task advance (`setTaskId` nulls `teacherHighlights` alongside the other per-student teacher-owned fields).

## Teacher Pane Highlight/Force: `teacherPaneCommand`

- Lets a teacher draw attention to, or immediately switch a student (or the whole class) to, a specific tab/panel a student might not have noticed — e.g. Electronics' Breadboard/MicroPython tabs, Scratch's Blocks/Stage tabs, or the Instructions/explainer pane on any lesson type.
- Triggered from `PaneFocusDropdown.jsx` — a checkbox picker of the panes relevant to the current lesson type ("Focus" per-student in `StudentModal.jsx`, "Focus Class" whole-class in `TeacherView.jsx`'s top bar) with two actions: **Highlight** and **Switch to this**.
- Two RTDB fields, same `{ mode: 'highlight' | 'force', panes: string[], pushedAt }` shape: `sessions/{lessonId}/students/{anonymousId}/teacherPaneCommand` (per-student, `pushTeacherPaneCommand`/`clearTeacherPaneCommand`) and `sessions/{lessonId}/teacherClassPaneCommand` (whole-class, `pushClassPaneCommand`/`clearClassPaneCommand`, every connected student evaluates the same node — same pattern as `teacherLive`). `StudentView.jsx` derives one effective command from whichever of the two has the more recent `pushedAt`.
- No consent step, unlike `teacherStageRequestedAt`/`teacherEditRequestedAt` — both modes apply immediately.
- `mode: 'highlight'` adds a pulsing glow (`pane-highlight-pulse` CSS class in `index.css`, animating `transform`/`filter` rather than `box-shadow` since `.ui-tab` forces that `!important`) to the named tab button(s)/collapse control, via a `highlightedIds`/`highlightedTabs`/`highlighted` prop threaded through `PanelTabs.jsx`, `ElectronicsWorkspace.jsx`'s tab buttons, and `CollapseTabButton`/`CollapsedPanelRail`/`ExplainerPanel`. Purely visual — nothing moves.
- `mode: 'force'` immediately switches the student's active tab/panel — applied once, through the same local-state path a manual click would use (not a persistent controlled prop), so the student stays free to navigate away again right after: `LessonTaskContent.jsx` sets `explainerCollapsed`/`accordionExplainerCollapsed` (and, if Scratch is in its compact tab layout, `taskPanelTab`) directly for the `instructions` pane; `ElectronicsWorkspace.jsx` and `ScratchWorkspace.jsx` each apply their own module-specific pane (`breadboard`/`code`, `blocks`/`stage`) via a `forcedTab`/`forcedPane` + `*Token` prop pair, guarded by the command's `pushedAt` so the same push never re-applies on an unrelated re-render. Skipped entirely on Electronics while `activeTab` is actively controlling the tab (teacher live-mirroring).
- Dismissal ("clears when the student looks at it") is tracked purely client-side in `StudentView.jsx` (`dismissedPaneCommandAt`), comparing the command's `panes` against the student's own reported `visiblePanes` — not by writing back to Firebase. This matters for the whole-class field specifically: it's one shared node, so one student looking at it must not clear it for the rest of the class.
- Cleared automatically on task advance (`setTaskId` nulls both `teacherPaneCommand` and `teacherClassPaneCommand`).
- Pane vocabulary per lesson type is defined once in `PaneFocusDropdown.jsx` (`PANE_OPTIONS_BY_TYPE`): `instructions` everywhere; `breadboard`/`code` (Electronics) and `blocks`/`stage` (Scratch) additionally. Other lesson types' own internal tabs (HTML file tabs, Python's console, Filesystem's explorer) aren't wired into highlight/force yet — only their Instructions pane is.

## Teacher Live Broadcast: `teacherLive`

- Separate from `activeStudentView`.
- Broadcasts the teacher's or a pinned student's screen to all students.
- Opens through `?teacher=true&present=true`.
- Broadcast code views stream selection/cursor plus copy, paste, and click notices.
- Scratch broadcasts stream the same block-activity notices, sprite/stage state, and live cursor as the Go-Live direction (see above) — the source is whichever `StudentWorkspace` instance is live-writing (the presenting teacher's own editor, or a pinned student's), since presentation mode (`?teacher=true&present=true`) renders the same `StudentWorkspace`/`ScratchWorkspace` pipeline students use, just with `teacherPresentation` flipping the publish gating to `source: 'teacher'`.
- `code_arrange` broadcasts a live drag mirror the same way Scratch does, so a Go-Live viewer sees tiles move as the teacher (or pinned student) drags them rather than the board snapping only once every blank is filled:
  - Every tile-placement change publishes to `teacherLive.codeArrangeSlots` (`handleCodeArrangeSlotsChange` in `useStudentCodeState.js`, alongside the existing per-student `currentCodeArrangeSlots` write for `StudentModal`). `CodeArrangeTaskContainer.jsx` reads it as `displayCodeArrangeSlots` and, for an `isForcedTeacherLive` viewer, prefers it over deriving the board from `displayCode` (which only updates once the whole arrangement is complete) — falling back to that derivation only if no live-slot payload has arrived yet.
  - An in-flight drag also streams its own position, broadcast-only (no per-student "watch one student" destination — `StudentModal` only needs the settled board): `CodeArrangeTask.jsx` reports `{ tileId, x, y, at }` (`x`/`y` normalized 0–1 against the task's own board container, throttled ~50ms via rAF, matching `CURSOR_THROTTLE_MS`) through `onDragCursor` → `handleCodeArrangeDragCursor` → `teacherLive.codeArrangeCursor` → `displayCodeArrangeCursor`. A read-only viewer renders it as a small dot plus a floating clone of the dragged tile (`DragCursorMirror` in `CodeArrangeTask.jsx`), fading out after 2s without an update (same as Scratch's cursor) and clearing immediately on drag end (`onDragCursor?.(null)`, fired from `useTileDragAndDrop`'s `onDragEnd` callback, which always runs after drop too since native `dragend` follows `drop`).
  - "Go Live for All" (`buildStudentLivePayload` in `teacherLivePayload.js`) seeds the initial `codeArrangeSlots` from the chosen student's own `currentCodeArrangeSlots` so the board isn't blank for the one frame before their next tile move.
  - A task change while live (`handleSoloNavigate`'s `updateTeacherLive({ taskId, ... })` reset) explicitly nulls both fields — `updateTeacherLive` is an RTDB `update()` (shallow merge), so without this a new task would otherwise inherit the previous code_arrange task's leftover slot/cursor state.
  - `CodeArrangeTask.jsx`'s "Drop here" invite text is gated on `canReceive && !blocked` for the student's own interactive board — but a viewer is *always* `blocked` (`disabled` prop, so real dropping there stays impossible), so a naive read of that same gate would never show the invite text during a mirrored drag, leaving empty slots looking inert while the ghost tile floats across them. Fixed by OR'ing in `externalDragCursor` on that gate (and folding `externalDragCursor?.tileId` into `activeId` alongside the local `draggingTile`/`touchSelectedTile`) — text-only, viewers still get no per-slot hover highlight (`isDragHighlight` stays local-only, always false there), so every eligible empty slot shows "Drop here" for the whole mirrored drag rather than narrowing to the one currently hovered.
- `onDisconnect` clears `teacherLive` automatically.

## Teacher Timers

- A task may define `estimatedMinutes` as a positive number (decimals allowed, e.g. `7.5`).
- Builder displays the lesson-wide estimated total.
- Starting a session sets `startedAt` and `currentTaskStartedAt`.
- Moving the class to a task or returning from sandbox restarts `currentTaskStartedAt`.
- Teacher view shows lesson elapsed time and a countdown for timed active tasks.
- Expired task timers flash.

## Remote Reset

- Teacher writes `remoteResetAction` and `remoteResetPushedAt` to one student node.
- Actions are `starter`, `complete`, or `stage_N`.
- Student detects timestamp changes and applies reset silently.
- `stage_N` resolves against `task.codeStages[N]`:
  - Python and Arcade Kit use `.code`; Arcade Kit also restores `.arcadeDesign`.
  - HTML uses `.files` and `.entryFile`.
  - Scratch uses `.blocks`, `.predefinedBlocks`, and `.prebuiltStacks`.
  - Electronics uses `.circuit`.
  - Filesystem uses `.fs`.

## Code Stage Reveal

- Python, HTML, Arcade Kit, Electronics, and Scratch code stages use `starter`, `support`, and `complete` roles. Multiple Starter stages are permitted; the first is the default and teachers can apply another Starter to an individual or the class. Legacy `core`, `extension`, and `solution` roles remain readable for existing lessons.
- Support stages are read-only references. Arcade Kit and Electronics show code only; Scratch support content is Markdown rendered with the Scratch-block renderer. They never replace the student's editor.
- Revealing a Support stage displays a read-only reference panel and never writes to the student's editor or files.
- Students are offered one Support stage after each failed run or check (including runtime and syntax errors). The offer remains until used or the student succeeds; repeated failures do not skip an unused reference. Only the newest revealed stage is displayed; a passing run/check hides it, and a later failure offers the next Support stage. Teachers can also reveal a stage reference for one student from `StudentModal`.
- Reveals write `supportRevealLog/{anonymousId}/{taskId}/{stageIndex}` with `source`, `stageLabel`, `attemptNumber`, and `revealedAt`.
- Teacher student cards mark the current task when a student has opened a reference. Session reports include per-student `supportReveals` and task-level reveal counts.
- A feedback check may instead target a particular current stage with `stageOffer: { stageIndex, action, afterMatches? }`. The lowest positive `priority` among matching feedback checks wins. `afterMatches` defaults to `2`. Accepting a stage action hides the feedback banner until the next evaluated attempt. `preview` is read-only; if the same targeted check matches again while its reference remains open, the next offer is to copy that stage into the student's work. `replace` always asks the student to confirm before overwriting their work. A different stage is not suggested while a reference is already open; targeted feedback also works for Python runtime errors when a code feedback check identifies the mistake.
- In the unified Python/HTML stage system, feedback checks may target Support stages only and always open a read-only hint; replacement is reserved for an already-previewed Complete stage.

## Complete-Code Reveal

Shows a read-only complete solution in the same reference panel as Support, without changing the student's actual editor. Python and HTML support this unified flow.

- **Live (class-wide)**: `session.explainerShowComplete` (boolean, session root) — toggled by the teacher from a control in `TeacherView.jsx` itself, rendered above `TeacherEditorPanel`/`TeacherCodeTabs` rather than inside that tab strip (`setExplainerShowComplete` in `useSession.js`). Affects every connected live student at once; there is no per-student variant. Resets to `false` on `setTaskId`, `createSession`, and `endSession`.
- **Solo (self-serve)**: after reference stages are exhausted and `checkFailCount >= 2`, the student is offered "See complete code?" (`canOfferCompletePreview` in `StudentView.jsx`) before the existing "Load complete code into my editor" offer (`canOfferCompleteSolution`). Clicking preview sets local-only `completePreviewShown` state (`useCheckFeedback.js` / `cs.handlePreviewCompleteCode` in `useStudentCodeState.js`) and replaces the current stage reference with a labelled complete reference — it does not touch the editor or mark the task solved. `completePreviewShown` resets on task change, code reset, or a passing check.
- The live teacher toggle alone feeds `explainerShowsComplete` into `LessonTaskContent.jsx`, which swaps `ExplainerPanel`'s `title`/`content` to a fenced ` ```python ` block of `task.completeCode`.
- Non-Python lesson types keep the original single-step "Load complete solution" offer (no preview step) since there's no read-only rendering for HTML/Scratch/filesystem solutions yet.

## Presenter Layout Toggle

- The presentation popup (`teacherPresentation`, `?teacher=true&present=true`) has a local-only three-way layout toggle in its top bar: **Explainer only / Both / Code only** (`presenterLayout` state in `StudentView.jsx`).
- Purely a display concern for that popup window — it hides/shows `LessonTaskContent`'s explainer pane and/or editor pane and is never persisted to Firebase or reflected to real students.

## Teacher-Forced Sandbox

- Student code is saved to localStorage before the editor clears on sandbox entry.
- Sandbox content is discarded on return to lesson and is never saved to localStorage.
- `sandboxCodePushedAt` and `sandboxFilesUpdatedAt` timestamps are change triggers.
- HTML sandbox stores files in Firebase `sandboxFiles` with `__dot__` encoded keys.
- Filesystem sandbox stores state as a JSON string in `sandboxCode`.
- Going live on a composed lesson can move `session.currentTaskId` to the sandbox module's first non-info/quiz task (`TeacherView.handleGoLiveSandbox`), so the right module/editor renders. `enterSandbox` records that prior task in `sandboxPreviousTaskId`; `exitSandbox` restores `currentTaskId` from it and clears the field, so the class returns to the task it was actually on before the sandbox push.

## Live Lesson Task Editing: `lessonOverrideTasks`

- `EditLessonModal` (launched from `TeacherSessionControls` → "Edit Lesson") reuses the builder's `TaskList`/`TaskEditor`/`GroupEditor`/`useBuilderState` to edit tasks without leaving TeacherView.
- Both TeacherView and StudentView compute an *effective* lesson via `applyLessonOverride(baseLesson, session?.lessonOverrideTasks)` — the fetched Firestore lesson with its `tasks` swapped for the live override when present. Every other lesson field is untouched.
- "Apply for This Session" (teacher or admin) calls `pushLessonOverride(tasks)`, writing to `sessions/{lessonId}/lessonOverrideTasks`. Currently connected students see the change immediately through their existing `useSession` listener — no page reload needed.
- "Save Permanently" (admin only) additionally calls `publishLessonTasks(lessonId, tasks)`, merge-writing `tasks` to the lesson's Firestore document, so future sessions start from the edited version too.
- Existing task IDs are never renumbered by this flow (`normalizeTasksForExport(tasks, { preserveIds: true })`) — `session.currentTaskId`, carry-through references, and student per-task localStorage keys all key off the original IDs and would desync if they changed mid-session. Only brand-new tasks get fresh IDs.
- "Reset to Original" calls `clearLessonOverride()`, reverting both views back to the canonical Firestore lesson.
- The override clears automatically on `createSession`/`endSession`, so a session restart always starts from the published lesson.

## Personal Sandbox

- Separate from teacher-forced `sandbox` session state.
- Available in both `lesson` and `solo` phases when the lesson defines sandbox starter content.
- Initial content comes from `lesson.sandboxStarterCode`, `lesson.sandboxStarterFiles`, or `lesson.sandboxStarterFs`.
- Persists in localStorage with pseudo-task ID `personalsandbox`.
- Survives task changes and teacher sandbox pushes.
- Solo mode shows "Open Sandbox" in navigation; closing returns to the lesson task.
- Live mode offers personal sandbox from `CheckFeedbackBanner` after a check passes.
- Teacher moving to the next task automatically returns live students to the lesson.
- Student writes `inPersonalSandbox: true` on entry and `null` on exit.
- Teacher sees personal sandbox state as a purple "Sandbox" badge in `StudentCard`.
- Task localStorage saves are skipped while in personal sandbox.
- Checks still run so the teacher can watch output, but results do not affect lesson progress.

## Pyodide

- Runs in a Web Worker and must not block the main thread.
- `stopPython()` terminates the worker to kill infinite loops.
- A replacement worker is pre-warmed immediately.
- `input()` is handled with a Python AST transform and resolves when `provideInput()` is called.

## Runtime Error-Line Highlight

- On a runtime error (Python traceback or an HTML/JS `window.onerror`), the failing line is highlighted red in the CodeMirror editor via `errorLineField`/`setErrorLine` in `src/shared/CodeEditor.jsx` (`.cm-errorLine` in `src/shared/codemirror.js`).
- Python: `formatPythonError` in `pyodide.worker.js` parses the innermost `File "<student>", line N` frame from the traceback and posts it as a structured `line` field alongside the existing stderr text; `useStudentCodeState`'s `errorLine` state drives the Python editor.
- HTML/JS: `iframe.js` embeds a per-load ID in the injected console interceptor and tracks the offset the injected CSP/console-interceptor script adds ahead of the entry file's own markup. `resolveIframeErrorLocation(loadId, filename, lineno)` maps a browser-reported `(filename, lineno)` back to `{ file, line }` — exact for external script files (unmodified content), offset-corrected for inline `<script>` errors in the entry file. `useStudentCodeState`'s `htmlErrorLocation` state (`{ file, line }`) drives the highlight only while that file's tab is active.
- When no clean line number can be determined (Pyodide startup failure, a raw `SyntaxError` before the student's `<student>` frame exists, or an HTML error whose file/line can't be confidently attributed), no highlight is shown — the error text still displays as before. A wrong highlight is treated as worse than no highlight.
- The highlight clears the moment the student edits the code (first keystroke), not just on the next Run — enforced both in the CodeMirror field (any document change clears it) and in `useStudentCodeState` (`errorLine`/`htmlErrorLocation` reset in `handleCodeChange`/`handleFileChange`).

## File Key Encoding

- Firebase file keys cannot contain raw dots.
- Use `encodeFileKey` and `decodeFileKey` when reading/writing `currentFiles` or `sandboxFiles`.
- App state and localStorage use raw filenames with real dots.

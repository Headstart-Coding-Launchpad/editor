# Agent Reference: Classroom Behaviours

Load this when a task touches student/teacher classroom behaviour, live view, broadcast, sandbox, Pyodide, or carry-through.

## Code Carry-Through

- Check localStorage for the authored carry source before loading starter content.
- If the immediate carry source has no saved state, walk the authored carry chain to the first earlier source with saved state. If the chain ends without saved state, use the current task starter content.
- Authored carry references can cross group boundaries; groups do not limit carry resolution.
- Saved empty content counts as real saved state; do not walk past it.
- HTML lessons carry each current `starterFiles` file independently by filename. Files not named in the current task remain hidden.
- Python and HTML use `carryCodeFrom`; Scratch uses `carryBlocksFrom`; filesystem uses `carryFsFrom`; electronics uses `carryCircuitFrom`.
- Live students write `carryFallbackLog/{anonymousId}/{taskId}` when carry-through walks past the immediate source and finds an earlier saved state. Session reports surface this as per-student `carryFallback` metadata plus task-level `carryFallbackCount`/`carryFallbacks`.
- Teacher presentation and builder preview persist to an in-memory ephemeral store (`ephemeralStorage` in `studentStorage.js`, routed via `createStudentPersistence`) so carry-through works there without reading or polluting real localStorage. The store is cleared on each presentation/preview mount. All persistence in these modes keys off `effectiveIdentity` (`teacher-presenter` in presentation).

## Live View: `activeStudentView`

- Default expanded student view shows the last-run snapshot only; it does not stream.
- Streaming starts only when the teacher clicks "Go Live".
- On "Go Live", fetch once first, then set `activeStudentView`.
- While live, teacher sees the student's selected text/cursor.
- Closing the modal by any route must clear `activeStudentView`: close button, outside click, Escape, or tab close.
- Firebase `onDisconnect` clears `activeStudentView` on unexpected teacher tab close.
- Only one student streams at a time.
- Scratch has the same live-view standard as Python/HTML, extended with sprite/stage motion and a live cursor:
  - Block drags, block clicks (click-to-run), green-flag, stop, and sprite drags on the stage surface are tracked as `currentActivity`/`teacherLive.activity` (generic `{ type, at }` shape, same as copy/paste/click) for other live-view logic (e.g. `StudentModal`'s live-file-follow); there is no longer a visible activity toast.
  - `ScratchWorkspace`'s stage canvas mirrors live sprite motion, not just authored starting positions: `onSpriteStatesChange` (`ScratchWorkspace.jsx`) publishes a throttled (~120ms) `{ spriteStates, cloneStates, backdropName }` snapshot to `currentSpriteState`/`teacherLive.spriteState`, and a read-only mirror instance loads it via the `externalSpriteState` prop without ever running the interpreter.
  - Block *content* mirroring is different from the sprite/cursor/block-drag mirrors above: those render purely from a mirror-only React state, but the `externalState`/`externalStates` "teacher push" effect calls `loadWorkspace` (`scratchPersistence.js`), which mutates the real, shared Blockly workspace object in place — there is no separate mirror instance to discard when the broadcast ends. `StudentWorkspace.jsx` (scratch module) therefore tracks the `isForcedTeacherLive` true→false edge and bumps a `liveEndEpoch` counter into `ScratchWorkspace`'s `key`, forcing a real remount so the workspace rebuilds from the student's own saved state — without this, the workspace keeps physically holding the teacher's last-broadcast blocks after "Go Live" ends, and the student's next edit persists them as their own saved code.
  - A live pointer dot tracks the source's mouse over the stage, the stage toolbar (green flag/stop/reset), the block palette (Blockly's flyout), and each sprite's Blockly block workspace (throttled ~50ms, `currentCursor`/`teacherLive.cursor`, shape `{ target: 'stage' | 'toolbar' | 'workspace' | 'flyout', spriteId, x, y, down, at }`). `stage`/`workspace`/`flyout` coordinates are scratch-space/Blockly-workspace-space (the flyout is a separate nested sub-workspace with its own pan/scroll, detected via `event.target.closest('.blocklyFlyout')` and converted through *its own* `screenToWsCoordinates` — converting through the main workspace's transform instead would place the dot at a meaningless, generally off-screen coordinate); `toolbar` coordinates are a plain pixel offset from the toolbar's own top-left corner (plain UI chrome, no stage-coordinate meaning), **not** a fraction of its bounding box — the toolbar container stretches to fill whatever width its flex layout gives it, but the buttons inside stay a fixed size and hug the left edge, so a fraction of the container's width points at a different button whenever the container is a different width on each viewer (e.g. compact vs non-compact stage layout) where a pixel offset from the shared, fixed-size button row does not. `down` (mouse button held, for the whole click/drag, not just the initial press — the stage's own pointermove used to skip re-sending the cursor entirely while a sprite drag was in progress, freezing it at the drag's start) layers a bigger, translucent yellow halo (`LiveCursorDot`) on top of the small pointer dot rather than recolouring the dot itself, so a click or an in-progress sprite/block drag reads differently from a plain hover without losing the dot's own marker; pointerdown/up transitions publish immediately rather than waiting on the throttle, so a plain click still flashes even without any movement. The mirror's visible sprite tab automatically follows the source's tab whenever a workspace- or flyout-target cursor is live. A cursor with no update for 2s fades out rather than freezing in place.
  - A block actively being dragged streams its own live position too (`currentBlockDrag`/`teacherLive.blockDrag`, `{ spriteId, blockId, x, y, at }`), read straight off Blockly's own drag-tracked coordinates and cleared to `null` when the drag ends — without this, the mirror only ever saw the settled block state on drop (debounced ~1s), so a dragged block would jump into place rather than visibly follow. The mirror moves the block via Blockly's `moveTo` (a plain reposition, not a real drag) and only if that block already exists in its last-synced state. Two things seed that last-synced state immediately instead of waiting on the presenter's first edit (previously: the *first* block drag after Go Live never visibly moved, only settling into place once the drag ended and the debounced sync caught up): `ScratchWorkspace.jsx` emits its just-loaded state once as soon as its Blockly workspaces are ready (not only on the next real edit), and `useTeacherLivePublish.js`'s `currentTeacherLivePayload` sources `code` from the Scratch work in `useStudentCodeState`'s generic work slot (what `handleScratchChange` last reported, `''` before any report on the task) rather than from another module's leftover code, so starting a broadcast, or switching the live task, doesn't publish stale code over the real one.
  - `externalState`/`externalStates` (the object `loadWorkspace` is called with) must stay reference-stable across renders that don't actually change the underlying code: a watching mirror re-renders on every throttled cursor/block-drag tick, and the "load external state" effect is keyed on object identity, so a freshly-parsed object every render would fully reload the mirrored workspace on each tick — stomping the live block-drag mirror's in-progress `moveTo()` with a stale reload a frame later. `StudentWorkspace.jsx` (scratch) and `StudentModal.jsx`'s `scratchState` both memoize the parsed state on the raw code string for this reason.

## Scratch Compact Layout: Instructions/Code and Blocks/Stage tabs

- The response to a shrinking panel is graduated, and — deliberately — the explainer gives way *before* the code area (Blocks/Stage) is ever forced to compact, not after. `LessonTaskContent.jsx` measures its explainer+workspace container (`useElementSize.js`, a `ResizeObserver` hook) and, for Scratch lessons only:
  1. **Split**: the explainer renders at a **fixed, non-resizable width** (`EXPLAINER_FIXED_WIDTH`, 320px — Scratch explainers often carry block-pill images/markdown that need real width) alongside the code area — no `SplitPane`, no drag handle, no percentage math. Deliberately simpler than a shrinking/pinning split: it's either 320px or a tab, nothing in between. This is a plain fixed-width flex layout, not a `SplitPane` change — every other lesson type (Python/HTML/Arcade/Electronics) still uses `SplitPane`'s draggable percentage split (`defaultSplit={26}`), untouched.
  2. **Instructions tabs away**: `LessonTaskContent` switches Instructions/Code to `PanelTabs` as soon as a fixed 320px explainer (plus the `s.scratchFixedSplit` gap between the two columns) would leave the code area under `ScratchWorkspace.jsx`'s own "wide" width — `EXPLAINER_FIXED_WIDTH + SCRATCH_SPLIT_GAP + SCRATCH_CODE_WIDE_WIDTH` (320 + 12 + 1000 = 1332px combined), where `SCRATCH_CODE_WIDE_WIDTH` is `ScratchWorkspace.jsx`'s exported `NARROW_BREAKPOINT`, imported rather than duplicated so the two thresholds can't drift apart. This is *before* the code area would otherwise be squeezed — the Code tab then gets the *entire* panel width, so Blocks/Stage stay side-by-side rather than being forced into their own compact tabs. Width-only: height doesn't factor in, since giving Code its own tab doesn't add height (explainer and code already share the same row).
  3. **Stage tabs away from Blocks — the final fallback**: only if the panel is so narrow that even giving Code the *entire* width still leaves it under `ScratchWorkspace.jsx`'s own `NARROW_BREAKPOINT` (1000px) does `ScratchWorkspace.jsx` — which independently measures its own real rendered container — switch to its own Blocks/Stage `PanelTabs` switcher, replacing the old `preferStageSidePanel`/auto-collapsing-stage-rail behaviour. No coordination code is needed for this step beyond the shared constant above — it otherwise falls out of each component measuring its own real rendered size. Width-only, same as step 2: a short-but-wide container doesn't trip this at all — it scales the stage down instead (see the `computeStageScale` note below). Unconditional for the teacher-modal `TeacherLiveView` (`forceCompact`, see below), regardless of width or height.
  The pre-existing manual explainer collapse-to-rail toggle (`explainerCollapsed`, `CollapseTabButton`/`CollapsedPanelRail`) still works within step 1, unrelated to any of the above — it's a separate, purely user-initiated affordance, not part of the automatic ladder.
  - **Solo-mode explainer pseudo-task**: in solo mode, whenever a Scratch task's explainer becomes hidden by *either* mechanism above (manual rail-collapse, step 2's auto tab-away) — i.e. `localVisiblePanes` no longer includes `'instructions'` — `StudentView.jsx` shows a synthetic "explainer slide" entry in the task nav, immediately before the task it belongs to (`makeExplainerPseudoTask`/`insertPseudoTaskBefore`/`isExplainerPseudoTaskId` in `src/shared/taskUtils.js`). The nav entry itself is debounced (~400ms) on appearing (so dragging the window across the auto-shrink breakpoint doesn't flicker the nav) but disappears immediately on re-expand, and is purely ephemeral client-side render state — nothing is persisted. Clicking it (or arriving with it already active, see below) sets `viewingExplainerSlide` (`StudentView.jsx`), which `LessonTaskContent.jsx` treats exactly like an authored `information` task (see the `isInformationTask` guards throughout that file) to render a read-only, full-page `InformationTask` for the current task's explainer instead of the split workspace. `TaskProgressDots.jsx` and `SoloNav.jsx` splice the pseudo entry into their task list rather than the real `lesson.tasks`/`flatTasks`, so it counts toward "Task X of Y" while present but never touches `currentTaskId`, Firebase, or check/progress state. Gated on `isSolo` and the current task's *effective* module type being Scratch (`activeLesson.type`, composed-aware via `getEffectiveLessonForTask` — composed lessons carry a per-task `moduleType`, not one `lesson.type`, so never gate this kind of check on the raw `lesson.type`).
  - **Arrival auto-show**: landing on a task (via Next, a nav dot, or the very first task on load) whose explainer is *already* hidden at that moment opens the slide automatically instead of dropping the student straight into the code — they then use the normal Next/dot controls to proceed past it, same as dismissing a manually-opened one. This is deliberately edge-triggered on `currentTaskId` changing (`pendingAutoShowTaskIdRef` in `StudentView.jsx`), not on the hidden-state itself, so resizing the window smaller while already sitting on a task never yanks the student back to the explainer mid-work — only a genuine navigation does.
- Tabs never unmount the inactive pane — this preserves live Blockly workspaces, a running Scratch program, and live-view mirroring (see below) regardless of which tab a student or viewer currently has open. `ScratchWorkspace.jsx`'s own Blocks/Stage tabs use the shared `PanelTabPanel` (`display:none` on the inactive one). `LessonTaskContent.jsx`'s outer Instructions/Code split does the same thing but *inline* rather than via `PanelTabPanel` — the explainer and code panes are the same two `<div>`s, in the same tree position, in *both* split and compact mode; only their `style` differs. This isn't just a style choice: if compact and split rendered structurally different trees at this position (as they briefly did — see the gotcha below), React would unmount and remount everything below on every threshold crossing, including every Blockly workspace inside `ScratchWorkspace`.
- The last-active tab is remembered per device via `localStorage` (`layoutTabStorageKey`/`loadLayoutTab`/`saveLayoutTab` in `studentStorage.js`, keys `headstart_layout_task_panel` and `headstart_layout_scratch_panel`) — unscoped, since it's a display preference rather than lesson/task state. With nothing yet persisted, the Instructions/Code switcher defaults to **Code** (the Blocks/Stage switcher defaults to **Blocks**) — a student landing in compact mode sees their workspace first, not the explainer.
- The wide-layout manual stage-panel rail-collapse (`stagePanelCollapsed`, the `CollapseTabButton`/`CollapsedPanelRail` pair) still exists above the compact threshold, but is now purely user-toggled — nothing auto-collapses or auto-restores it. The stage toolbar's `CollapseTabButton` is always rendered (in compact mode, styled `visibility: 'hidden'` rather than omitted) so it still reserves its layout width — omitting it outright in compact mode shifted the green flag/stop/reset buttons after it left by its width, so they landed in a different horizontal position than in the non-compact layout.
- The teacher dashboard's "watch one student" modal (`StudentModal` → `StudentWorkspaceBody.jsx`) renders `scratch/TeacherLiveView.jsx`, which always forces the compact Blocks/Stage layout (`forceCompact`) regardless of the modal's own width — this replaced a direct, non-compact `ScratchWorkspace` render that could show a different collapsed panel than the student's own screen at the same width.
- `code_arrange` tasks are the analogous case for `StudentModal`: `deriveTaskContext()` (`src/shared/taskUtils.js`) only derives `isPython`/`isHtml` from the lesson module type, so a `code_arrange` task still trips those flags. `StudentWorkspaceBody.jsx` checks `isCodeArrangeTask` (`isModuleHostedActivityTask(task)`, from the activity registry) before the `isPython`/`isHtml` branches and renders the code_arrange activity's `TeacherLiveView` — the real `CodeArrangeTask` tile board (`src/activities/code_arrange/`) — read-only, with `selectedAnswer` reconstructed from `student.currentCode`/`currentFiles` via `deriveSlotStateFromCode()` (`src/shared/codeArrange.js`) — instead of falling through to a raw read-only `CodeEditor` showing the fully assembled program text, which didn't match what the student was dragging tiles into.
- The student grid (`StudentCard.jsx`) shows a "👀 Info + Blocks + Stage"-style badge summarising what a student can currently see, live-synced to `sessions/{lessonId}/students/{anonymousId}/visiblePanes` via `writeStudentPresence`. Every lesson type feeds this now, via two different paths in `LessonTaskContent.jsx`:
  - **Scratch** (the original case, where the explainer/code split itself hides a pane): `ScratchWorkspace.jsx` derives its own `['blocks']`/`['stage']`/`['blocks','stage']` from `hideStage`/`compact`/`activePane`/`stagePanelCollapsed` and reports it via `onVisiblePanesChange`; `LessonTaskContent.jsx` combines that with its own Instructions/Code tab state (`taskPanelCompact`/`taskPanelTab`) into the final array, held in its `scratchCodePanes` state.
  - **Electronics, Python, Arcade, HTML** (module-internal toggles, gated by `MODULE_PANES_TYPES`): each module's own `StudentWorkspace.jsx` reports its togglable state directly into `LessonTaskContent.jsx`'s generic `modulePanes` state via the same `onVisiblePanesChange` prop — Electronics reports `[selectedTab]` (`'breadboard'`/`'code'`, via `ElectronicsWorkspace.jsx`'s `onTabChange` effect, which also fires for the teacher-controlled `activeTab` prop); Python reports `['code']` or `['code','console']` from `outputCollapsed` (only when the output pane is actually rendered — never for submit-mode tasks); Arcade reports `[workspaceTab, ...(running ? ['running'] : [])]`; HTML reports `[activeFile, ...(previewVisible ? ['preview'] : [])]` (the file name passes straight through `StudentCard.jsx`'s `VISIBLE_PANE_LABELS` map unmapped, since file names are dynamic).
  - **The `instructions` entry itself** is computed once, centrally, in `LessonTaskContent.jsx` (`instructionsPaneVisible`) and merged into whichever of the two paths above applies — it does *not* come from a module's own `onVisiblePanesChange` report. It's `false` whenever the task has no explainer at all (quiz/information/personal sandbox, or a teacher-forced sandbox with no pushed `sandboxExplainer`); otherwise it follows whichever collapse mechanism is actually rendered: the compact tab (`taskPanelTab === 'instructions'`), the side-rail collapse (`!explainerCollapsed`, Scratch and every other `SIDE_EXPLAINER_TYPES` lesson type on desktop), or `ExplainerPanel`'s own accordion collapse (`!accordionExplainerCollapsed`, reported upward via its `onCollapsedChange` prop — used by Filesystem, which has no side-rail layout, and by every type's mobile fallback).
  - **Filesystem** has no `MODULE_PANES_TYPES`/side-explainer entry and reports no internal panes of its own — but it still reports `['instructions']`/`[]` (via the `instructionsPaneVisible` merge above, gated on `hasTaskExplainer` alone rather than `isScratchLesson`/`supportsModulePanes`), so its Info badge still works even though it has nothing else to report yet.
  In both paths, `LessonTaskContent.jsx` hands the final array to `StudentView.jsx`'s `onVisiblePanesChange`, which writes to Firebase only for a real student in a live/sandbox session (never `teacherPresentation`), deduped against the last-written value.
- **Gotcha #1 — stale measurement across task navigation**: `TaskSlideTransition.jsx` keys its child wrapper by `transitionKey` (one per task), so on every task navigation React tears down and rebuilds the panel's DOM node *without* `LessonTaskContent` itself remounting — its hooks (and any state they hold) persist across that swap. `useElementSize.js` therefore uses a callback ref, not `useRef` + a mount-only effect: a plain effect would only ever have attached to the very first task's DOM node, then silently kept "observing" that now-detached node forever, freezing the measured size (and therefore the compact-tab decision) at whatever it happened to be on the first task loaded — intermittent-looking bug reports ("sometimes it's compact, sometimes it isn't, I can't tell why") after navigating between tasks trace back to this. `ScratchWorkspace.jsx` doesn't have this problem — its `StudentWorkspace.jsx` caller gives it a task-scoped `key` too, so it *does* fully remount (deliberately, to re-inject Blockly) and its own resize effect sets up fresh each time.
- **Gotcha #2 — remounting ScratchWorkspace on every compact/split crossing**: earlier revisions rendered the outer Instructions/Code split and the outer Instructions/Code tabs as structurally different trees (one used `PanelTabPanel`, the other plain `<div>`s) at the same position in `LessonTaskContent.jsx`. Since these differ in element/component type, React can't reconcile between them — every time `taskPanelCompact` flipped (i.e. every time the panel crossed the 1332px boundary while resizing), it unmounted the *entire* subtree below, including `ScratchWorkspace` and every Blockly workspace it had injected, then mounted a fresh instance. A freshly-mounted `ScratchWorkspace` starts non-compact until its own `ResizeObserver` reports back — normally self-corrects within a frame, but repeated remounts (e.g. resizing back and forth across the boundary a few times) could leave it stuck showing Blocks/Stage as tabs even at a width where it should be side-by-side, matching reports like "the stage stays collapsed until everything is wide open." Fixed by keeping the explainer/code panes as the same two `<div>`s regardless of mode (see above) — see `src/app/components/__tests__/LessonTaskContent.test.jsx`'s mount-count regression test.
- **Blockly zoom is fully automatic — there is no manual wheel-zoom or on-canvas zoom control.** `ScratchWorkspace.jsx` continuously recomputes a block scale (`computeBlockScale(width, height)`, a pure exported function) from the same container measurement used for `compact`, between `BLOCK_SCALE_MAX` (0.75, the old fixed default) at/above the wide reference size and a `BLOCK_SCALE_MIN` readability floor (0.6) as the container shrinks within compact territory — applied via `ws.setScale()` on every sprite's workspace inside `resizeBlocklyWorkspaces`. Manual zoom was removed deliberately (not just left disabled) so this auto-adjustment never has a student's own zoom choice to fight, mirroring why the stage-panel auto-collapse was replaced with tabs rather than kept as an auto-toggle. The mouse wheel now pans instead of zooming.
- **A shrinking panel scales the stage instead of hiding it or forcing a scroll.** `scratchTaskPanelWrap` carries no height floor (`minHeight: 0`, same as every other fluid-workspace lesson type) — a taller sibling (a status banner appearing above the workspace, etc.) is free to shrink it as far as it needs to. (The check-feedback popup itself is `position: fixed` and floats over the page rather than sitting in this flow — see "Check Feedback Popup" below — so it no longer affects this sibling's height.) `ScratchWorkspace.jsx`'s `computeStageScale(width, height, { compact, flyoutCollapsed })` (pure, exported, unit-tested) takes the *smaller* of a width-derived and a height-derived scale factor — the height factor reserves `STAGE_TOOLBAR_HEIGHT_RESERVE` (52px) for the stage toolbar above the canvas — so the stage's rendered size shrinks continuously down to a `MIN_STAGE_SCALE` (0.35) floor as height drops, the same way it already shrunk with width. This replaced an earlier approach (a hard `minHeight` floor on `scratchTaskPanelWrap`, propagated through two ancestors via `minHeight: 'auto'` overrides, `TaskSlideTransition`'s now-removed `panelStyle` prop among them) that kept `ScratchWorkspace` from ever measuring short — which avoided tripping the old height-based compact threshold, but did so by making the page scroll to keep the panel at its floor height, which could scroll the stage out of view entirely. Compact itself is now width-only (see step 3 above); height is handled entirely by scaling.
- **Stage emoji fallback rendering can flip fonts on first paint.** A sprite/clone without a costume image falls back to drawing its `emoji` field on the canvas (`drawEmojiAtOrigin`), styled `'Noto Color Emoji', serif` — a Google Fonts web font loaded page-wide via `index.css`'s `@import` (`font-display: swap`). Canvas text doesn't repaint itself once a swapped-in web font finishes loading the way DOM text does — whatever font was available at the moment `fillText()` ran is what stays drawn, even after the real font loads, until something else happens to trigger a redraw. `ScratchWorkspace.jsx` explicitly awaits `document.fonts.load(...)` once per mount and bumps `imageVersion` (the same "force a stage redraw" counter the backdrop/costume image-preload effects use) once it settles, so both the stage canvas and the `SpriteThumb` sprite-panel thumbnails (which already redraw on `imageVersion`) always end up showing the correct emoji font rather than whichever one happened to be ready first.

## Teacher Code Highlights: `teacherHighlights`

- Independent of `activeStudentView`/`teacherLive` — a teacher watching a student live (`StudentModal`) can select a character range in the mirrored, read-only `CodeEditor` and tag it with an emoji + optional short note.
- Stored as a map at `sessions/{lessonId}/students/{anonymousId}/teacherHighlights/{highlightId}` (RTDB `push()` keys, so any number can coexist across files/lines) — written by `pushTeacherHighlight`/`removeTeacherHighlight` in `useSession.js`.
- Each entry: `{ file (encodeFileKey'd), from, to, emoji, note, createdAt }`. Python tasks use an empty string for `file` (single-file, no tabs).
- Renders as a `Decoration.mark` + clickable emoji badge (`teacherHighlightsField` in `src/shared/CodeEditor.jsx`) in **both** the teacher's mirror and the student's own editable editor — the same dual-instance path `remoteSelection` already uses.
- Badges float in the empty space past the end of the highlighted line: one zero-size inline anchor per line (multiple highlights on a line share a pill row) with the pills absolutely positioned, so a highlight never shifts the student's code, changes line height, or covers code. Do not reintroduce an inline-flow widget for the badge.
- Clicking the emoji badge removes that highlight (`onHighlightDismiss`) — this lets the teacher retract their own highlight from the mirror, or the student dismiss it from their own editor. Either side writes the same RTDB removal.
- Editing inside a highlight clears it for good: a user edit (typing, deleting, pasting, undo — `USER_EDIT_EVENTS`) that inserts inside, deletes part of, or replaces the highlighted text drops it from `teacherHighlightsField` and the editor calls `onHighlightDismiss` — the same RTDB removal as clicking the badge, so the teacher's mirror drops it too. Typing right at either edge, or deleting text that only borders it, keeps it (edges are non-inclusive) and it moves with the code. Changes from outside (task switch, a live mirror update) only map highlights, never dismiss them.
- Ranges are character offsets valid for the document as of creation; CodeMirror remaps them through edits. `CodeEditor` compares the `teacherHighlights` prop by content (like `lineHints`), because the array is rebuilt from every session snapshot — including the student's own `currentSelection` writes while the teacher has the modal open. Only a real change to the set reaches the editor, and then a highlight already shown keeps its mapped position (the stored one predates the edits); only new ones use the stored offsets. Do not re-dispatch the stored offsets on every prop change — that is what made highlights jump around as the student typed. Highlights the editor cleared stay cleared while the session still lists them (dismissal in flight).
- `CodeEditor` applies an outside `value` change as one minimal change (shared prefix/suffix untouched, `minimalReplace`) rather than a whole-document replace, so the teacher's mirror maps its highlights through each live code update instead of briefly losing them.
- The stored offsets are not rewritten as the student edits, so a highlight can still drift if the editor is remounted after edits elsewhere in the file (student reload, or the teacher reopening the modal later) — accepted tradeoff for character-exact (vs line-snapped) precision.
- Cleared automatically on task advance (`setTaskId` nulls `teacherHighlights` alongside the other per-student teacher-owned fields).

## Teacher Pane Highlight/Force: `teacherPaneCommand`

- Lets a teacher draw attention to, or immediately switch a student (or the whole class) to, a specific tab/panel a student might not have noticed — e.g. Electronics' Breadboard/MicroPython tabs, Scratch's Blocks/Stage tabs, or the Instructions/explainer pane on any lesson type.
- Triggered from `PaneFocusDropdown.jsx` — a checkbox picker of the panes relevant to the current lesson type (`PaneFocusControls` as the Focus section of the per-student More menu in `StudentModal.jsx`, `PaneFocusDropdown` as "Focus Class" whole-class in `TeacherView.jsx`'s top bar) with two actions: **Highlight** and **Switch to this**.
- Two RTDB fields, same `{ mode: 'highlight' | 'force', panes: string[], pushedAt }` shape: `sessions/{lessonId}/students/{anonymousId}/teacherPaneCommand` (per-student, `pushTeacherPaneCommand`/`clearTeacherPaneCommand`) and `sessions/{lessonId}/teacherClassPaneCommand` (whole-class, `pushClassPaneCommand`/`clearClassPaneCommand`, every connected student evaluates the same node — same pattern as `teacherLive`). `StudentView.jsx` derives one effective command from whichever of the two has the more recent `pushedAt`.
- No consent step, unlike `teacherStageRequestedAt`/`teacherEditRequestedAt` — both modes apply immediately.
- `mode: 'highlight'` adds a pulsing glow (`pane-highlight-pulse` CSS class in `index.css`, animating `transform`/`filter` rather than `box-shadow` since `.ui-tab` forces that `!important`) to the named tab button(s)/collapse control, via a `highlightedIds`/`highlightedTabs`/`highlighted` prop threaded through `PanelTabs.jsx`, `ElectronicsWorkspace.jsx`'s tab buttons, and `CollapseTabButton`/`CollapsedPanelRail`/`ExplainerPanel`. Purely visual — nothing moves.
- `mode: 'force'` immediately switches the student's active tab/panel — applied once, through the same local-state path a manual click would use (not a persistent controlled prop), so the student stays free to navigate away again right after: `LessonTaskContent.jsx` sets `explainerCollapsed`/`accordionExplainerCollapsed` (and, if Scratch is in its compact tab layout, `taskPanelTab`) directly for the `instructions` pane; `ElectronicsWorkspace.jsx` and `ScratchWorkspace.jsx` each apply their own module-specific pane (`breadboard`/`code`, `blocks`/`stage`) via a `forcedTab`/`forcedPane` + `*Token` prop pair, guarded by the command's `pushedAt` so the same push never re-applies on an unrelated re-render. Skipped entirely on Electronics while `activeTab` is actively controlling the tab (teacher live-mirroring).
- Dismissal ("clears when the student looks at it") is tracked purely client-side in `StudentView.jsx` (`dismissedPaneCommandAt`), comparing the command's `panes` against the student's own reported `visiblePanes` — not by writing back to Firebase. This matters for the whole-class field specifically: it's one shared node, so one student looking at it must not clear it for the rest of the class.
- Cleared automatically on task advance (`setTaskId` nulls both `teacherPaneCommand` and `teacherClassPaneCommand`).
- Pane vocabulary per lesson type is defined once in `PaneFocusDropdown.jsx` (`PANE_OPTIONS_BY_TYPE`): `instructions` everywhere; `breadboard`/`code` (Electronics) and `blocks`/`stage` (Scratch) additionally. Other lesson types' own internal tabs (HTML file tabs, Python's console, Filesystem's explorer) aren't wired into highlight/force yet — only their Instructions pane is.

## Presentation Annotations: `liveInk`

- From the Presentation window (`?teacher=true&present=true`, `StudentView` with `teacherPresentation`) the teacher can annotate **information tasks** (standard, recap and introduction, images included) and the **explainer pane of code tasks**, and every student in the live lesson sees it as it happens. Whole class only.
- A small floating toolbar (`PresentationInkToolbar.jsx`, bottom centre) appears only in the Presentation window, and only while something annotatable is on screen (an information task, or a code task whose explainer is visible — a collapsed explainer unmounts its surface and the toolbar goes). Tools: **🔴 Pointer** (a dot that follows the mouse), **✏️ Ink** (freehand marks that fade a few seconds after being drawn), **🖍️ Highlight** (select text; it stays highlighted until clicked again, cleared, or the task changes) and **Clear**. Escape leaves the current tool. Pointer and Highlight modes don't block normal clicks; Ink mode puts a capture layer over the content so a drag draws instead of selecting. Highlight mode lifts the copy-block's `user-select: none` on the teacher's own content only.
- Positions are content-relative, not pixels: each mark names a surface (`info:{taskId}`, `recap-left:…`, `recap:…`, `intro:…`, `explainer:{taskId}`) and a `data-md-anchor` element from the shared Markdown renderer, with fractions of that element's box — so on a smaller screen the dot still sits on the same word or the same part of an image. Highlights store the selected text plus which occurrence of it, and are re-found on each screen. Data shape, lifetimes and rules: `docs/agents/runtime-model.md`, "Presentation Annotations".
- Students: `LiveInkOverlay` draws over the content with `pointer-events: none` (nothing to click, nothing in the way). If the teacher's pointer (or a mark from the last few seconds) is outside the student's scrolled view, an edge chip "👆 Teacher is pointing here ↑/↓" appears; clicking it scrolls there. The view **never** auto-scrolls.
- Annotating a code task's explainer (pointer entering it, a new stroke or highlight) pushes the existing whole-class pane command (`pushClassPaneCommand({ mode: 'force', panes: ['instructions'] })`, see "Teacher Pane Highlight/Force") so students with the explainer collapsed see it open; re-pushed at most every 8 s so a student can still close it.
- Motion: the pointer is lightly smoothed (lerp per animation frame) between the ~12Hz updates; strokes hold then fade with a CSS animation. Under `prefers-reduced-motion` the pointer jumps and strokes simply disappear at the end of the same lifetime, with no fade.
- Annotations are cleared on every task change (`setTaskId`), on session create/restart/end, by Clear, and when the Presentation window closes or disconnects. Surface ids include the task id, so even a late write can't land on the next task.
- Code: `src/app/liveInk/` — `LiveInkProvider.jsx` (subscription, tool state, toolbar; wraps `StudentView`'s page), `InkSurface.jsx` (wraps content in `InformationTask.jsx` and `ExplainerPanel.jsx` via its `inkSurfaceId` prop; inert without a provider, so the Builder, solo study, `StudentModal` and the teacher's main view are untouched), `LiveInkOverlay.jsx`, `geometry.js` (pure box/fraction and quote helpers), `liveInkData.js`, `liveInkWriter.js`.

## Teacher Live Broadcast: `teacherLive`

- Separate from `activeStudentView`.
- Broadcasts the teacher's or a pinned student's screen to all students.
- Opens through `?teacher=true&present=true`.
- Broadcast code views stream selection/cursor plus copy, paste, and click notices.
- Scratch broadcasts stream the same block-activity notices, sprite/stage state, and live cursor as the Go-Live direction (see above) — the source is whichever `StudentWorkspace` instance is live-writing (the presenting teacher's own editor, or a pinned student's), since presentation mode (`?teacher=true&present=true`) renders the same `StudentWorkspace`/`ScratchWorkspace` pipeline students use, just with `teacherPresentation` flipping the publish gating to `source: 'teacher'`.
- `code_arrange` broadcasts a live drag mirror the same way Scratch does, so a Go-Live viewer sees tiles move as the teacher (or pinned student) drags them rather than the board snapping only once every blank is filled:
  - Every tile-placement change publishes to `teacherLive.codeArrangeSlots` (`handleCodeArrangeSlotsChange` in `useStudentCodeState.js`, alongside the existing per-student `currentCodeArrangeSlots` write for `StudentModal`). `CodeArrangeTaskContainer.jsx` reads it as `displayCodeArrangeSlots` and, for an `isForcedTeacherLive` viewer, prefers it over deriving the board from `displayCode` (which only updates once the whole arrangement is complete) — falling back to that derivation only if no live-slot payload has arrived yet.
  - An in-flight drag also streams its own position, broadcast-only (no per-student "watch one student" destination — `StudentModal` only needs the settled board): `CodeArrangeTask.jsx` reports `{ tileId, x, y, at }` (`x`/`y` normalized 0–1 against the task's own board container, throttled ~50ms via rAF, matching `CURSOR_THROTTLE_MS`) through `onDragCursor` → `handleCodeArrangeDragCursor` → `teacherLive.codeArrangeCursor` → `displayCodeArrangeCursor`. A read-only viewer renders it as a small dot plus a floating clone of the dragged tile (`DragCursorMirror` in `CodeArrangeTask.jsx`), fading out after 2s without an update (same as Scratch's cursor) and clearing immediately on drag end (`onDragCursor?.(null)`, fired from `useTileDragAndDrop`'s `onDragEnd` callback, which always runs after drop too since native `dragend` follows `drop`).
  - "Go Live for All" (`buildStudentLivePayload` in `teacherLivePayload.js`) seeds the initial `codeArrangeSlots` from the chosen student's own `currentCodeArrangeSlots` so the board isn't blank for the one frame before their next tile move.
  - A task change while live (`handleSoloNavigate`'s `updateTeacherLive({ taskId, ... })` reset) explicitly nulls both fields — `updateTeacherLive` is an RTDB `update()` (shallow merge), so without this a new task would otherwise inherit the previous code_arrange task's leftover slot/cursor state.
  - `CodeArrangeTask.jsx`'s "Drop here" invite text is gated on `canReceive && !blocked` for the student's own interactive board — but a viewer is *always* `blocked` (`disabled` prop, so real dropping there stays impossible), so a naive read of that same gate would never show the invite text during a mirrored drag, leaving empty slots looking inert while the ghost tile floats across them. Fixed by OR'ing in `externalDragCursor` on that gate (and folding `externalDragCursor?.tileId` into `activeId` alongside the local `draggingTile`/`touchSelectedTile`) — text-only, viewers still get no per-slot hover highlight (`isDragHighlight` stays local-only, always false there), so every eligible empty slot shows "Drop here" for the whole mirrored drag rather than narrowing to the one currently hovered.
- **Task slides follow the direction of travel.** `TaskSlideTransition.jsx` takes the displayed task's flat index as `order` (`StudentView.jsx` passes it through `LessonTaskContent.jsx`'s `transitionOrder`, so solo, live and the `?present=true` presentation window all get it): a later task enters from the right and the old one leaves to the left, an earlier task the reverse; an unknown order (the personal sandbox, a shared workspace) slides forward. The direction class only sets `--task-slide-dir`, so the reduced-motion rule (no slide, leaving copy hidden) covers both. The teacher's own view slides only the task explainer, keyed by the previewed/current task: the editor, broadcast and side panels have side effects, so they swap in place rather than being remounted in a leaving copy.
- **A leaving task slide never writes onto the next task.** `TaskSlideTransition.jsx` remounts the previous task's element tree in its outgoing panel, with that task's stale props and callbacks, *after* the next task's work has loaded into the shared work slot. Stateful workspaces read `useIsLeavingTaskSlide()` and render as a detached visual snapshot: Scratch's `StudentWorkspace.jsx` (no saves or check reports), and `CodeArrangeTaskContainer.jsx`, which otherwise reloaded its saved arrangement and pushed the assembled program through `cs.handleCodeChange` / `handleFileChange` — into the next code task's editor (only when the arrangement was complete, so it looked intermittent) — and re-published its slots. Its `detached` flag drops saves, slot mirroring, assembled-code pushes, Run/input and remote Runs while leaving the display unchanged. A `code_arrange` task is still a legitimate carry-through source: a code task with `carryCodeFrom` naming it starts from the assembled program by design.
- **A complete `code_arrange` board and the code slot never disagree.** Run and the attempt log read the shared code slot, never the tiles, and the slot can be reset under a mounted board (a live task load restoring the empty starter after the board pushed, a late identity reloading the task, a teacher reset). `CodeArrangeTaskContainer.jsx` therefore compares the assembled program against the real slot (`getCodeArrangeSlotCode()`, `src/shared/codeArrange.js`) and re-pushes whenever they differ (not while running or in the personal sandbox); `handleRun` in `useStudentCodeState.js` assembles from the last reported tiles first as a safety net. A teacher `starter` / `complete` remote reset also resets the tiles: the hook exposes `codeArrangeReset` (`{ slots, taskId, at }`, the activity's `initialState` / `solutionState`, never re-applied from history), which the container applies and acknowledges. A board only counts as complete when every blank holds a tile from the task's own pool (`isArrangementComplete`; stored boards are pruned by `pruneSlotState` on load), and an HTML task's assembled program creates its entry file if the work lacks it (`handleFileChange`). Output and check feedback are not cleared when tiles move after a run — same as an ordinary Python task's edits.
- **Quiz and activity tasks are teacher-only broadcasts.** "Go Live for All" (broadcasting a student) is not offered in `StudentModal` on quiz or hosted-activity tasks (`allowsStudentBroadcast` in `src/activities/registry.pure.js`; `code_arrange` keeps it), `TeacherView.handleGoLiveForAll` refuses it, and a student broadcast still running from an earlier code task stops publishing once the student reaches such a task (`canPublishTeacherLive`). A running broadcast can always be stopped. The teacher's own Presentation View broadcast on an activity task publishes the serialised state as `teacherLive.answer`; viewers read it as `displayAnswer` and `ActivityHost` renders it read-only.
- `onDisconnect` clears `teacherLive` automatically.
- **The output/preview panel's expand-collapse state mirrors too, continuously (locked, not a one-time seed).** Python and Electronics' console `OutputPanel` and HTML's iframe preview each publish their collapse toggle to `teacherLive.outputCollapsed` via `publishOutputCollapsed` (`useTeacherLivePublish.js`) — a standalone `update()` merge rather than routed through the main payload, since `outputCollapsed` should persist across every other field's publish without every call site needing to know about it. A forced-live viewer reads it back as `displayOutputCollapsed` (`studentLiveDisplay.js`) instead of their own local toggle state, and their own collapse/expand controls are hidden or inert while forced-live — they cannot diverge from what the source has open. Not wired for Arcade's `OutputPanel` usage (`ArcadePreview.jsx`), which relies on `OutputPanel`'s own internal collapsible header rather than an externally-controlled toggle — a different plumbing shape that would need its own change.
- **Students can't copy the broadcast.** While a student is watching a broadcast, the mirrored workspace is unselectable: `deriveStudentLiveDisplay` returns `isLiveCopyBlocked`, which `LessonTaskContent.jsx` turns into a `live-copy-blocked` class on the same `editorArea` wrapper that already carries `live-view-active`.
  - The flag is deliberately narrower than `isForcedTeacherLive`: it is `isTeacherLiveViewer || isStudentGoLiveViewer` only. The third case `isForcedTeacherLive` folds in, `isPresentationStudentViewer`, is the *presenting teacher* watching a pinned student on their own screen, and a teacher keeps normal selection.
  - Covers the editor area (code editor, file tabs, console output) and the instructions/explainer panel beside it, which gets the same class and copy/cut cancelling — it can carry a pushed sandbox explainer or the complete-code reveal.
  - The HTML preview iframe is a separate document parent CSS can't reach, so the viewer's preview is built with `buildIframeSrc(..., { copyProtect: true })` (`useTeacherLivePublish.js`): an end-of-body style + script that disables selection and cancels `copy`/`cut`/`contextmenu`/`dragstart` (right-click would offer "View frame source").
  - CSS `user-select: none` is necessary but not sufficient: CodeMirror's content stays `contenteditable` while read-only (`EditorState.readOnly` doesn't remove it), so Ctrl+A / Ctrl+C still builds a real selection the browser will copy. `editorArea` therefore also cancels `copy`/`cut`/`dragstart` in the **capture** phase (`onCopyCapture` etc.) and stops propagation, which closes the keyboard, right-click and drag-out routes in one place rather than per module. It must be the capture phase: CodeMirror's own copy/cut handler on its content element writes the selection into `clipboardData` itself, so cancelling the event once it bubbles back out is too late.
  - The teacher's mirrored selection still renders: it's a `.cm-remoteSelection` decoration (`src/shared/codemirror.js`), not a native browser selection.
  - Deterrent, not enforcement, and deliberately silent — no toast, no banner line, no teacher notice. Devtools, a second device and retyping are all still open; those are classroom management, not a code problem. There is no toggle and no lesson field: it is always on while a broadcast is up.
  - Not applied to approved shared workspaces (`SharedWorkspaceViewer` renders with `isForcedTeacherLive={false}` and doesn't pass the flag) or to the teacher's own `StudentModal` watch view.
- **Large pastes are flagged, not blocked.** `LessonTaskContent`'s workspace wrapper listens for `paste` bubbling out of a CodeMirror editor (`.cm-editor`) and hands the text to `cs.handleEditorPaste`. In a live lesson (not solo, sandbox, presentation or preview) a paste of at least 40 characters or 3 lines (`src/shared/pasteDetection.js`) is counted via `recordStudentPaste` into the student's own `pasteLog/{taskId}` (`{ count, chars, lastAt }`). Text the student copied or cut from their own editor (remembered from `copy`/`cut` on the same wrapper) doesn't count, so moving their own code around isn't flagged. The teacher sees "📋 Pasted" on the StudentCard (current task) and StudentModal, and the session report shows it per student task and per task.

## Teacher Answer Editing: `teacherAnswerEdit`

- For Match, Fill in the Gaps, and Code Arrange tasks (and activities with `teacherEditable`), `StudentModal` shows an "✏️ Edit answers" toggle. The student sees a brief "✏️ Your teacher updated your answer" notice and nothing else.
- Teacher side only: attempts logged on that task carry `teacherAssisted`, the report shows "Passed (teacher assisted)" plus a per-task "N teacher assisted" count, and `StudentCard`/`StudentModal` show an Assisted badge while `teacherAssistedTaskId` matches the current task. Any teacher edit on a task marks it assisted for the rest of that task in that tab.

## Teacher Remote Run: `remoteRunPushedAt`

- `StudentModal` shows "▶ Run on student" for Python, Turtle, Arcade, HTML (not submit-mode), Scratch, and Electronics tasks, including Code Arrange; disabled while the student is offline. It writes `remoteRunPushedAt`/`remoteRunTaskId` via `pushRemoteRun`.
- The program runs on the **student's** device, never in the teacher's browser. `useStudentCodeState` consumes the request (clears it in Firebase first, so a reload never re-runs it) and exposes `remoteRunToken`; each module workspace calls `useRemoteRunTrigger` with the exact action its own Run button uses — Python/Turtle `handleRunClick` (opens the output panel), HTML/Electronics `cs.handleRun`, Arcade `run()`, Scratch the green-flag `handleRun` (via `ScratchWorkspace`'s `runToken` prop), Code Arrange `cs.handleRun` only once the arrangement is complete — and acknowledges the token back to null.

## Code Stage Reveal

- Python, HTML, Arcade Kit, Electronics, and Scratch code stages use `starter`, `support`, and `complete` roles. Multiple Starter stages are permitted; the first is the default and teachers can apply another Starter to an individual or the class. Legacy `core`, `extension`, and `solution` roles remain readable for existing lessons.
- Support stages are read-only references. Arcade Kit and Electronics show code only; Scratch support content is the stage's `markdown`, rendered with the Scratch-block renderer (an empty panel if the stage has none). Revealing never replaces the student's editor; a Scratch stage's `blocks` are only loaded by an explicit replace (teacher stage push, `stageOffer` `replace`, stage reset).
- Revealing a Support stage displays a read-only reference panel and never writes to the student's editor or files.
- Students are offered one Support stage after each failed run or check (including runtime and syntax errors). The offer remains until used or the student succeeds; repeated failures do not skip an unused reference. Only the newest revealed stage is displayed; a passing run/check hides it, and a later failure offers the next Support stage. Teachers can also reveal a stage reference for one student from `StudentModal`.
- Reveals write `supportRevealLog/{anonymousId}/{taskId}/{stageIndex}` with `source`, `stageLabel`, `attemptNumber`, and `revealedAt`.
- Teacher student cards mark the current task when a student has opened a reference. Session reports include per-student `supportReveals` and task-level reveal counts.
- A feedback check may instead target a particular current stage with `stageOffer: { stageIndex, action, afterMatches? }`. The lowest positive `priority` among matching feedback checks wins. `afterMatches` defaults to `2`. Accepting a stage action hides the feedback banner until the next evaluated attempt. `preview` is read-only; if the same targeted check matches again while its reference remains open, the next offer is to copy that stage into the student's work. `replace` always asks the student to confirm before overwriting their work. A different stage is not suggested while a reference is already open; targeted feedback also works for Python runtime errors when a code feedback check identifies the mistake.
- In the unified Python/HTML stage system, feedback checks may target Support stages only and always open a read-only hint; replacement is reserved for an already-previewed Complete stage.

## Teacher-Live-Code Reference

Shows Presentation View's currently-typed code as a live, dismissible reference in the same panel as Support/Complete, without forcing a takeover of the student's editor. Covers Python, HTML, Arcade Kit, Electronics, and Filesystem — not Scratch (its live "code" is a serialized Blockly project, not text).

- Presentation View (`teacherPresentation` mode) continuously publishes its own code to `sessions/{lessonId}/teacherLiveReference` (`active`, `taskId`, `code`/`files`) via `useTeacherLivePublish.js`, cleared via Realtime Database `onDisconnect` and on unmount when Presentation closes — deliberately separate from `session.teacherLive`, which drives the unconditional whole-class "Go Live" force takeover (`isForcedTeacherLive`). The reference channel keeps publishing regardless of whether Go Live is toggled on.
- The teacher shows it in one of two modes (a student sees it when either applies):
  - **One-off reveal** (drops off between tasks, like a stage reveal): "Reveal live code" in `StudentModal`'s Support → Reveal section, next to the stage reveals, or "Reveal live code to all" (with a confirm, like a stage's "Reveal to all") on the "Live" tab that `TeacherCodeTabs.jsx` adds alongside Starter/Stage/Complete in `TeacherEditorPanel.jsx`. Either writes `supportRevealLog/{anonymousId}/{currentTaskId}/teacherLive` (`TEACHER_LIVE_REVEAL_KEY`, `source: 'teacher'`): per student the teacher writes it via `recordSupportStageReveal`; for the class every student is sent the `reveal_live` remote-reset action, which the student's client applies (local state at once plus the same log write — only while Presentation is broadcasting that task). That log entry *is* the reveal state, so the reference shows on that task only and no clearing write is needed on task change. The menu item then reads "Opened: live code".
  - **Pinned** ("📌 Keep showing live code" per student in the Support menu's "Show on every task" section / "📌 Keep showing live code to class" on the Live tab): `students/{anonymousId}/teacherLiveReferenceVisible` / `session.teacherLiveReferenceVisibleToAll`, written by `setTeacherLiveReferenceForStudent` / `setTeacherLiveReferenceForClass` in `useSession.js` as the time it was pinned (legacy `true` still counts). `setTaskId` leaves both alone, so it keeps showing on every task until turned off. The active state reads "📌 Live code: kept on" (menu button, Live-tab button, and a `StudentModal` header chip); the student's panel label gains a 📌.
- The Live tab is shown only while Presentation View is actually broadcasting the displayed task, and reads that same broadcast read-only when selected. Both modes' controls are disabled until Presentation is on that task (unpinning always works).
- A student only sees it when requested (pinned, or a one-off reveal logged for their current task) **and** `session.teacherLiveReference.taskId` matches their current task **and** they are not already under an `isForcedTeacherLive` takeover (`teacherLiveReferenceActive` / `teacherLiveReferencePinned` in `useStudentCodeState.js`, adapted into the panel shape by `teacherLiveReferenceStageFrom` in `LessonTaskContent.jsx`). This makes it auto-clear the instant Presentation closes or moves to a different task — no explicit clear write needed.
- Reveal logging (what the teacher's "Support" chip on `StudentCard` and the session report count): a one-off reveal logs once on the task it was revealed on (`teacherLive`, `source: 'teacher'`). A pin logs **once per pin**, not per task: on the first task the pinned reference actually shows, the student's client writes `supportRevealLog/{id}/{taskId}/teacherLivePinned` (`TEACHER_LIVE_PIN_REVEAL_KEY`, `source: 'teacher-auto'`, `pinnedAt` = the pin value) and skips any later task whose log already holds that `pinnedAt` (`isTeacherLivePinLogged`). Unpinning and pinning again is a new pin and logs again. The pin entry is display-only — it never shows the reference by itself. Trade-off: a badge rule that looks for reveals on a task (Challenge Solver's `noSupportReveal`) only sees the pin on the task it was logged on.

## Complete-Code Reveal

Shows a read-only complete solution in the same reference panel as Support, without changing the student's actual editor. Python and HTML support this unified flow.

- **Live (class-wide)**: `session.explainerShowComplete` (boolean, session root) — toggled by the teacher from a control in `TeacherView.jsx` itself, rendered above `TeacherEditorPanel`/`TeacherCodeTabs` rather than inside that tab strip (`setExplainerShowComplete` in `useSession.js`). Affects every connected live student at once; there is no per-student variant. Resets to `false` on `setTaskId`, `createSession`, and `endSession`.

(`canOfferCompletePreview` in `StudentView.jsx`) before the existing "Load complete code into my editor" offer (`canOfferCompleteSolution`). - The live teacher toggle alone feeds `explainerShowsComplete` into `LessonTaskContent.jsx`, which swaps `ExplainerPanel`'s `title`/`content` to a fenced ` ```python ` block of `task.completeCode`.
- Non-Python lesson types keep the original single-step "Load complete solution" offer (no preview step) since there's no read-only rendering for HTML/Scratch/filesystem solutions yet.

## Check Feedback Popup & Need Help

## Teacher-Forced Sandbox

- Student code is saved to localStorage before the editor clears on sandbox entry.
- Sandbox content is discarded on return to lesson and is never saved to localStorage. It is no longer thrown away entirely, though: for the session report (a possible lesson gap), each teacher-sandbox visit is archived teacher-side in the top-level RTDB `sessionArchive/{lessonId}` — when the class went in and out, the task it followed, the teacher's explainer and every push, and each student's last sandbox code, copied from the `currentCode` / `currentFiles` their sandbox runs already write (capped at 20 KB each). Nothing subscribes to it and students cannot read it. See `docs/agents/runtime-model.md`, "Badge data".
- Sandbox runs, sandbox time, topic opens and keyboard shortcuts in the sandbox are counted (never the code) in the student's `studentSignals`, for the Live Badges (Code Fixer, Resourceful Coder, Keyboard Wizard). Personal sandboxes are counted the same way, as activity only.
- `sandboxCodePushedAt` and `sandboxFilesUpdatedAt` timestamps are change triggers.
- HTML sandbox stores files in Firebase `sandboxFiles` with `__dot__` encoded keys.
- Every other module stores its sandbox work in `sandboxCode` through its definition's `wire.toCode` (read back with `wire.fromCode`): the code itself for Python, Turtle, Arcade and Electronics (its serialised circuit), a JSON string for Scratch (`'{}'` before any block), Filesystem and Desktop. TeacherView keeps the teacher's work and draft per `capabilities.sandboxState` kind (`src/app/teacherSandboxWork.js`); the channel comes from `wire.sandboxChannel` (`docs/architecture/lesson-type-modules.md`, "teacher surfaces").
- Going live on a composed lesson can move `session.currentTaskId` to the sandbox module's first non-info/quiz task (`TeacherView.handleGoLiveSandbox`), so the right module/editor renders. `enterSandbox` records that prior task in `sandboxPreviousTaskId`; `exitSandbox` restores `currentTaskId` from it and clears the field, so the class returns to the task it was actually on before the sandbox push.
- Because `session.currentTaskId` still names a lesson task during sandbox, sandbox code must never be scored against it: `useStudentCodeState.handleRun` skips check/test evaluation and sends `checkPassed: undefined` (leaving any earlier result untouched) while `phase === 'sandbox'` or in a personal sandbox. Teacher-side `StudentCard`, `StudentGrid` counts, and `StudentModal` hide pass/fail while `session.state === 'sandbox'`, and the Python `StudentWorkspace` ignores the task's submit mode, tests, check badge, and copy-code panel.
- The teacher's pushed `sandboxExplainer` takes the task explainer's place in `LessonTaskContent` (same side-by-side collapsible layout, highlight/force support), and sandbox keeps the fluid workspace layout even when the session task is a quiz/information task.
- The student top bar keeps the normal control group in sandbox (Need Help, shared-work gallery) with "Download sandbox code" replacing "Download code" for Python. Reset Code returns Python/Turtle sandbox code to the teacher's `sandboxCode` (falling back to `lesson.sandboxStarter`), not the session task's starter.

## Live Lesson Task Editing: `lessonOverrideTasks`

- `EditLessonModal` (launched from `TeacherSessionControls` → "Edit Lesson") reuses the builder's `TaskList`/`TaskEditor`/`GroupEditor`/`useBuilderState` to edit tasks without leaving TeacherView.
- Both TeacherView and StudentView compute an *effective* lesson via `applyLessonOverride(baseLesson, session?.lessonOverrideTasks)` — the fetched Firestore lesson with its `tasks` swapped for the live override when present. Every other lesson field is untouched.
- "Apply for This Session" (teacher or admin) calls `pushLessonOverride(tasks)`, writing to `sessions/{lessonId}/lessonOverrideTasks`. Currently connected students see the change immediately through their existing `useSession` listener — no page reload needed.
- "Save Permanently" (admin only) additionally calls `publishLessonTasks(lessonId, tasks)`, merge-writing `tasks` to the lesson's Firestore document, so future sessions start from the edited version too.
- Existing task IDs are never renumbered by this flow (`normalizeTasksForExport(tasks, { preserveIds: true })`) — `session.currentTaskId`, carry-through references, and student per-task localStorage keys all key off the original IDs and would desync if they changed mid-session. Only brand-new tasks get fresh IDs.
- "Reset to Original" calls `clearLessonOverride()`, reverting both views back to the canonical Firestore lesson.
- The override clears automatically on `createSession`/`endSession`, so a session restart always starts from the published lesson.
- The override tasks are sealed like the lesson document (`pushLessonOverride` seals, `applyLessonOverride` unseals); see the next section.

## Sealed Lesson Answers: obfuscation, not security

- Task answers (complete code and stages, checks, feedback checks, tests, quiz answers, code_arrange blanks) are stored sealed in `task._sealed` on the public `lessons/{id}` document and in `lessonOverrideTasks` (format: `docs/agents/runtime-model.md` "Sealed Task Answers"). This stops casual snooping in the Network tab or a raw Firestore payload. It is **not** security: the key ships in the app bundle, and the classroom unseals the whole lesson at load, so React DevTools (or a determined student) can still see the answers.
- Anything the classroom needs keeps working because every consumer reads through `decodeLessonFromFirestore` / `applyLessonOverride`; never read `lessons` docs or `lessonOverrideTasks` without them.
- The teacher's live broadcast (`teacherLive.code` / `files`, and a forced Complete reset or answer edit) still travels in plain text: the student client must render and run that code, so it cannot be sealed usefully.

## Personal Sandbox

- Separate from teacher-forced `sandbox` session state.
- Available in both `lesson` and `solo` phases when the lesson defines sandbox starter content.
- Initial content comes from `lesson.sandboxStarterCode`, `lesson.sandboxStarterFiles`, or `lesson.sandboxStarterFs`.
- Persists in localStorage with pseudo-task ID `personalsandbox`.
- Survives task changes and teacher sandbox pushes.
- Solo mode shows "Open Sandbox" in navigation; closing returns to the lesson task.
- Live mode offers personal sandbox from `CheckFeedbackBanner` after a check passes.
- Teacher moving to the next task automatically returns live students to the lesson.
- Student writes `inPersonalSandbox: true` on entry and `null` on exit.
- Teacher sees personal sandbox state as a purple "Sandbox" badge in `StudentCard`.
- Task localStorage saves are skipped while in personal sandbox.
- Runs still mirror output so the teacher can watch, but Python/Turtle/Electronics runs are not scored against the lesson task (no `checkPassed` write, no attempt log), so a pass earned before opening the sandbox is not overwritten.

## Solo Lesson Completion Screen

- This specific screen is solo mode only (never live/presentation) — a live session ends when the teacher ends it, not when the student runs out of tasks, so there's no equivalent "reached the end" moment mid-session. The live analogue is the "Session ended" screen below.
- A synthetic "lesson complete" nav entry (`makeCompletionPseudoTask`/`isCompletionPseudoTaskId` in `src/shared/taskUtils.js`) is reachable via Next off the last real task, same splice-into-nav mechanism as the Scratch explainer pseudo-task above, but appended *after* the last task instead of before one, and applies to every lesson type, not just Scratch.
- Purely ephemeral render state (`viewingCompletionScreen` in `StudentView.jsx`) — like the explainer slide, it never touches `currentTaskId`, so it can't interfere with persistence, Firebase, or checks. `currentTaskId` stays pinned to the real last task throughout.
- Only spliced into `flatTasksForNav` once the student has actually reached the last real task (`currentIndex === flatTasks.length - 1`) or is already viewing it — not for the whole lesson — so it doesn't inflate "Task X of Y" until it's actually reachable. `SoloNav`'s `displayTotal` prop keeps that label showing the real task count right up until the completion screen itself is being viewed.
- Rendered by `LessonTaskContent.jsx` via `isViewingCompletionScreen`, gated identically to `isViewingExplainerSlide` throughout that file (no side explainer, no code pane, no support-stage reveals) but showing `LessonCompleteScreen.jsx` instead of `InformationTask` — a fixed "Lesson complete!" message, not authored content.
- Shows an "Open Playground" button when the *last code task in the lesson* (skipping any trailing information/quiz tasks, via `isCodeTask`) resolves — through `getTaskModuleType`, composed-aware — to one of `PLAYGROUND_LESSON_TYPES` (`src/shared/composedLesson.js`: `python`, `arcade`, `electronics`, `scratch` — the types with a `/playground/:type` route). No button for `html`/`filesystem`, which have no playground. Deliberately not `activeLesson.type`/`currentTaskId`: on a composed lesson those are frozen on the last *real* task at completion time, which may be a trailing non-code task with no module of its own, or an earlier module than the one the student actually finished coding in.
- Also shows "Go Through the Lesson Again" (navigates back to the first task via the normal `handleSoloNavigate` path — backward navigation is never restricted, so this doesn't touch saved progress) and, when the lesson has a linked solo companion (see below), "Try the Solo Challenge".
- The buttons navigate via `window.location.hash` (same pattern as the teacher's Account Settings link in `TeacherSessionControls.jsx`), not `useNavigate`, so `StudentView.jsx` doesn't take on a React Router dependency.

## Workspace Sharing

- Opt-in per task: the student's "📤 Share with class" button only exists where the author set `allowSharing: true`.
- Live lessons only. Never shown in solo, sandbox, builder preview, teacher presentation, or to a forced teacher-live viewer.
- The student's own client builds the snapshot (`buildShareSnapshot` in `useStudentCodeState`), because `currentCode` is only fresh for the watched student. See the Workspace Sharing section of `docs/agents/runtime-model.md`.
- The button shows "⏳ Waiting for teacher" while a request is pending; clicking again withdraws it.
- Declining is silent — the button simply becomes available again, with no message. A student cannot tell a decline from a withdrawal.
- The teacher reviews a frozen snapshot in `ShareRequestPanel`, deliberately labelled as such: it is not the live watch view, and may already differ from what the student is doing now.
- While a share is pending, that panel **replaces** the student modal's live workspace body rather than sitting above it. Showing both invited approving one while reading the other, and only the snapshot is what the class would receive. The live workspace returns once the request is approved or declined.
- The teacher can also start a share from the More menu without the student asking. That stamps `shareSnapshotRequestedAt`; the student's device answers silently with a fresh snapshot and the same preview/Approve step follows. No student consent step, unlike `teacherEditRequestedAt`.
- Approved shares appear in a "📤 Shared work (n)" gallery, tagged with the task they came from, and survive task changes until the teacher removes them.
- A new approved share raises a toast. Dismissal is tracked client-side only — one student dismissing must not clear it for the class, the same constraint as `teacherClassPaneCommand`. Shares already present when a student joins count as seen, so joining mid-lesson does not fire a backlog.
- A student never gets a toast for their own share.
- A shared workspace opens **in place of** the student's own workspace, in the same layout slot, with a banner naming whose work it is and a "Back to my work" control.
- It renders the student's **own** surface — the same `LessonTaskContent` and module `StudentWorkspace` they use for their own work — not a bespoke viewer and not the teacher-facing `TeacherLiveView`. Those have different chrome and controls (Electronics most visibly), so anything hand-built drifts from what the student knows. `SharedWorkspaceViewer` therefore delegates to `LessonTaskContent` and parity is structural rather than maintained by hand.
- Opening a shared workspace is non-destructive **by construction**. The surface is driven by a second, throwaway `useStudentCodeState` instance configured so no write can escape it: `previewMode: true` routes persistence to the in-memory ephemeral store instead of real localStorage; the `lessonId` is namespaced (`shared-workspace::{shareId}`) so the ephemeral store cannot collide with the student's own work or another share; every session writer is a no-op, so no path to Firebase exists; and `phase: 'solo'` keeps the live-session write paths disengaged.
- The snapshot is seeded into the ephemeral store (`seedSharedWorkspace`) **before** that hook mounts, so each module's normal "load my saved work" path picks it up. That is what keeps every lesson type working through its real code path rather than a parallel one — code modules seed `{ code }`, Scratch seeds `{ state }`, HTML seeds one entry per file, Filesystem seeds the fs slot, Arcade adds `arcadeDesign`.
- The viewer renders by the snapshot's own `lessonType` and `taskId`, not the viewer's current task — a share outlives its task, and in a composed lesson may be a different module entirely.
- "Copy to my editor" is the only bridge into the student's real work. It is confirmed first, and offered only when the snapshot's task matches the task they are on.
- A student currently viewing a share writes their real `writeStudentInteraction({ viewingShareId })` to `sessions/{lessonId}/students/{anonymousId}` — separate from the throwaway viewer state above, which never reaches Firebase. `StudentCard` shows a "👀 {sharerName}" badge live on the roster while `student.online && student.viewingShareId`; gating on `online` means a stale field from a dropped connection just stops rendering rather than sticking. Set on open, cleared (`null`) on close or on copying into their own editor.
- The teacher gets the same read-only look at an approved share that students get: `TeacherSessionControls`' "📤 Shared work" dropdown has an **Open** button per entry (alongside Remove) that fetches the snapshot and renders it in a modal via the same `SharedWorkspaceViewer`, just without `onCopyToMyEditor` — a teacher has no editor of their own to copy into.

## Video Call Prompt

`VideoCallPrompt.jsx` ("Your teacher wants you on the video call", Join / Not now) pops up when the teacher pushes the session's `videoCallLink`, either to one student (`students/{id}/videoCallLinkPushedAt`, StudentModal **More → 📹 Send Video Call Link**) or to everyone (`videoCallBroadcastAt`, **📹 Send to all** beside the Video Call control). `useVideoCallPrompt` (called once in `StudentView`) decides when it shows:

- **Where.** Name entry, the waiting room, and the lesson/sandbox page (every task type). Name-entry students have no student record, so only the broadcast reaches them. Never in solo, the choice or end screens, or the presentation window. The waiting room's static "Join Video Call" button stays as well.
- **Load baseline.** Both timestamps present when the session first loads are a baseline, as in `useNudgeAlert`, so a reload never replays an old push. A push older than `VIDEO_CALL_PROMPT_STALE_MS` (10 minutes) by the student's clock is ignored.
- **Pushes while hidden are consumed.** A push that lands while the prompt can't show (e.g. on the choice screen) is marked seen, not queued.
- **Tied to its phase.** The prompt closes when the student's phase changes (name entry → waiting room → lesson) and does not come back, so a waiting-room prompt never pops up again once the lesson starts. A new push in the new phase shows it again.

## Live Badge Celebration

The student side of the tutor's badge decisions (`sessions/{lessonId}/badges`), driven by `useBadgeCelebrations` in `StudentView`, with the decisions logic in `src/badges/celebration.js`. See `docs/architecture/live-badges-plan.md`, "Student experience".

- **Load baseline.** Every `awarded` decision present when the session first loads is seen, as in `useNudgeAlert` and the shared-work toast, so a reload or a late join replays nothing. An award's identity includes its `decidedAt`, so a badge revoked and then awarded again is celebrated again. Awards arriving outside the lesson/sandbox phases are marked seen too, never queued for later.
- **Recipient.** A new award for this student queues a card (`BadgeCelebration`): a small card drops down top-centre just under the top bar (`sv-badge-layer--top`), flips in with one shine sweep for `CELEBRATION_CARD_MS` (2.5 s), then docks into the compact 🎖️ moments button (`CodingMomentsPill`, `data-badge-dock`; icon-only, no count, its popover holds the moments and the mute). Several awards queue one at a time. A card whose award is revoked before it shows is dropped silently.
- **Never steal focus.** Nothing in the card is focusable, the card-sized layer is `pointer-events: none` (only the card itself takes pointer events, so nothing around it is blocked), and a mousedown on the card is cancelled so the editor keeps focus. The announcement goes through an always-mounted `aria-live="polite"` region; the card itself is `aria-hidden`. `prefers-reduced-motion` (a JS check adding `sv-badge-card--reduced`, plus a CSS media query) swaps the flip, shine and dock for a fade.
- **Chime.** `playBadgeChime()` (the `badge` preset of `playChime` in `nudgeAlert.js`, low gain) plays as each card starts, skipped when `badgeSettings.soundsOff` is on or the student muted. The mute is the app-wide Sounds setting (`useSoundsMuted` in `src/app/soundSettings.js`, localStorage `headstart_sounds_muted`), shared with the top-bar 🔊/🔇 `SoundsToggleButton` and the complete chime.
- **Complete chime.** `useCompleteChime` (called in `StudentView`) plays `playCompleteChime()` (the `complete` preset: C5-E5-G5, about 400 ms) the first time the displayed task's checks pass while the student watches, solo and live. It keys off `usePassMoment`, ignores passes within `COMPLETE_CHIME_ARRIVAL_GRACE_MS` (1.5 s) of arriving on a task (restores and reloads), and remembers per screen which task keys already chimed, so a later fail → pass is silent; "Show complete" marks the task as chimed first. Disabled for the presentation window, `previewMode` and the personal sandbox; respects the student's mute and `badgeSettings.soundsOff`. The nudge chime is not a celebration and ignores the Sounds mute.
- **Class toast.** `BadgeClassToast`, bottom-left (the shared-work toast owns bottom-right), silent, "🎖️ Alex earned a badge: 🐛 Bug Hunter" (`classToastLabel` after `CLASS_TOAST_ICON`), a slide-in with one soft glow, `CLASS_TOAST_MS` (4 s) with the blurb only in its `title`. Only `announce: true` decisions toast; the recipient never gets one. Decisions sharing a `bulkId` merge into one toast with a recipient count ("🎖️ 12 students earned a badge: …"), including pieces that arrive in later snapshots while it is queued or showing; once a bulk's toast has finished it never toasts again, and a bulk the viewer is part of gives them the card instead. New toasts beyond `CLASS_TOAST_QUEUE_CAP` (5, the showing one included) are dropped.
- **Presentation window.** `viewerId` is null there: toasts only (`sv-badge-toast--presentation`, scaled up for the board, `PRESENTATION_TOAST_MS` 4.5 s), never a card, moments button or chime.
- **Session end.** `endSession` keeps `badges`, so `SessionEndedScreen` lists the student's own `awarded` badges (`listMyMoments`) as a `BadgeStickerSheet`. A returning student (their identity's `lastSessionTimestamp` matches the session's `createdAt`) who reloads within `END_SCREEN_RESTORE_MS` (3 h) of `endedAt` goes back to the end screen instead of the Join/Solo choice (`useStudentPhase`).
- **Badge Summary task.** An information task with `informationType: badges` renders `BadgeSummaryTask` through `InformationTask`'s `badgeWall` prop: `StudentView` passes `{ decisions, students, viewerId, variant }` in the live `lesson` phase only (`variant: 'presentation'`, no viewer, on the presentation window), `TeacherEditorPanel` the teacher variant with Copy class summary, and the Builder nothing (a preview note). The wall is `buildClassWall` (`src/badges/badgeSummary.js`): awarded decisions grouped by badge, names from the roster, no counts. In solo, `filterTasksByMode` drops the task (`getEffectiveTaskMode` treats it as `taskMode: live`), so solo navigation and the lesson-complete screen never reach it.
- **Stacking.** Card layer `z-index` 1240: above the shared-work toast and nudge permission prompt (1200), below the nudge banner (1250) and the consent/teacher-message modals (1300). Class toast 1150, so the one-time nudge permission prompt (also bottom-left, 1200) sits over it if both show.
- **Teacher 👍.** Not a badge: a transient "you're on the right track". The 👍 on a `StudentCard` (online students) or in the `StudentModal` header calls `sendThumbsUp`, stamping `students/{id}/thumbsUpPushedAt` (cleared by `setTaskId`); the button shows ✓ and is disabled for 2 s. `useThumbsUp` in `StudentView` (same gate as nudges: lesson/sandbox, not the presentation window) takes a load baseline like `useNudgeAlert`, ignores pushes older than 30 s, plays `playBadgeChime()` unless muted or `soundsOff`, and shows `ThumbsUpToast` top-centre (`z-index` 1245, `motion-pop-in`, `role="status"`, `pointer-events: none`, no focus change) for 2.5 s. Never shown to the class, never in session reports or the badge decisions.
- **Catalogue badges.** Students can't read Firestore `badgeCatalogue`, so an awarded catalogue badge carries its `{ emoji, title, blurb }` on the decision (`decision.badge`), and `resolveBadge` renders it from that snapshot.

## Pyodide

- Runs in a Web Worker and must not block the main thread.
- `stopPython()` terminates the worker to kill infinite loops.
- A replacement worker is pre-warmed immediately.
- `input()` is handled with a Python AST transform and resolves when `provideInput()` is called.
- `useStudentCodeState`'s `resetForTaskChange()` calls `runtime.stop()` (and force-clears `running`/`runningTests`) whenever a run is still in flight when the student navigates to another task — a python/electronics execution must not keep running (or its output bleed into the new task) after the task changes. The `'stopped'` result from a run that raced with navigation is only repainted into `output`/`runStatus` if `currentTaskId` still matches the task that was running.

## Runtime Error-Line Highlight

- On a runtime error (Python traceback or an HTML/JS `window.onerror`), the failing line is highlighted red in the CodeMirror editor via `errorLineField`/`setErrorLine` in `src/shared/CodeEditor.jsx` (`.cm-errorLine` in `src/shared/codemirror.js`).
- Python: `formatPythonError` in `pyodide.worker.js` parses the innermost `File "<student>", line N` frame from the traceback and posts it as a structured `line` field alongside the existing stderr text; `useStudentCodeState`'s `errorLine` state drives the Python editor.
- HTML/JS: `iframe.js` embeds a per-load ID in the injected console interceptor and tracks the offset the injected CSP/console-interceptor script adds ahead of the entry file's own markup. `resolveIframeErrorLocation(loadId, filename, lineno)` maps a browser-reported `(filename, lineno)` back to `{ file, line }` — exact for external script files (unmodified content), offset-corrected for inline `<script>` errors in the entry file. `useStudentCodeState`'s `htmlErrorLocation` state (`{ file, line }`) drives the highlight only while that file's tab is active.
- When no clean line number can be determined (Pyodide startup failure, a raw `SyntaxError` before the student's `<student>` frame exists, or an HTML error whose file/line can't be confidently attributed), no highlight is shown — the error text still displays as before. A wrong highlight is treated as worse than no highlight.
- The highlight clears the moment the student edits the code (first keystroke), not just on the next Run — enforced both in the CodeMirror field (any document change clears it) and in `useStudentCodeState` (`errorLine`/`htmlErrorLocation` reset in `handleCodeChange`/`handleFileChange`).

## File Key Encoding

- Firebase file keys cannot contain raw dots.
- Use `encodeFileKey` and `decodeFileKey` when reading/writing `currentFiles` or `sandboxFiles`.
- App state and localStorage use raw filenames with real dots.
